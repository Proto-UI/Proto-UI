You do not need to understand the whole repository before contributing. You do need a task whose boundary matches what you can safely decide.

The repository [CONTRIBUTING.md](https://github.com/Proto-UI/Proto-UI/blob/main/CONTRIBUTING.md) contains the exact human workflow. This section explains how the pieces fit together.

## Choose by readiness

Starter work has a fixed result and little protocol judgment. Contributor-ready work has decided semantics but may still require substantial implementation. Maintainer-guided work still contains an admission, ownership, compatibility, or architecture decision.

Effort does not answer readiness. A small task can be blocked on design; a large slice can be ready to implement.

Before claiming anything, read the Issue, recent comments, assignee, linked pull requests, and Project state when it becomes available. If the outcome, exclusions, implementation authorization, or validation boundary is missing, ask for the task to be shaped first.

## Pick a path

- [Collaboration model](/en/contribute/collaboration/) explains what Issues, labels, Projects, milestones, reviews, and Actions each own.
- [Deliver a change](/en/contribute/deliver/) covers development, acceptance, regression, deployment, and release.
- [Contributor Agents](/en/contribute/agents/) explains the composable skill system, capability assessment, and autonomous task selection.
- [Agent skill catalog](/en/contribute/skills/) lists every lazy state transition and its role.
- [Agent automation](/en/contribute/automation/) separates deployed shadow tasks, manual protocols, and candidate recurring work.
- [Prototype authoring](/en/build/prototypes/) covers governed component work in detail.

Questions and early ideas belong in [GitHub Discussions](https://github.com/Proto-UI/Proto-UI/discussions). Bounded work belongs in [GitHub Issues](https://github.com/Proto-UI/Proto-UI/issues). Discord is useful for quick coordination, but implementation-changing decisions should be recorded back in the repository.
