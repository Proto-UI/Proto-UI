Data Table composes passive Table topology with stable record IDs, stable sorting, global filtering, pagination and row selection. Rows are authored presentation slots indexed within the current page; cells render their columnKey from the current record, so sort changes update actual content without pretending CSS order changed Table structure. App-owned rows must have unique id values. The composition does not own fetching, editing or column reordering.

WIP functional source. Full runtime/Compiler/native, packaging, browser and visual acceptance remain pending.

Sorting headers belong inside the static `DataTableHeaderRow` composition. It inherits passive Table Row topology, has no props or instance exposes, and creates no selection, focus or Trigger owner. Body rows remain `DataTableRow` record slots. The legacy `DataTableRow.header` prop still changes record-slot policy at runtime; it does not remove that row's setup-time Trigger identity and cannot contain multiple direct Trigger children. The examples use the new static composition without relaxing Trigger-chain rules.

## Filter, visibility, selection and formatting recipe

The following recipe uses public Input and Button controls with the same DataTable parts. Name filtering combines with Root `filter`; each nonempty `columnFilters` entry must match before sorting and pagination. `columnVisibility` hides a column’s physical Header and Cell views while retaining their authored logical coordinates. Hidden headers cannot receive sorting focus, and hidden Header and Cell views are excluded from accessibility presentation. The authored parts and custom children retain their identity when shown again.

`requestPageSelection()` selects or clears only the current filtered page, preserves selections on other pages, and reports `pageSelection` as `none`, `some` or `all`. Controlled `selectedKeys` remains request-only; `readOnly` rejects row and page selection while still allowing sorting and pagination. Empty-page requests are no-ops.

A Cell with `renderValue={false}` keeps application-authored children. Its public `displayValue` still follows the current record, including replacement data with the same ID. This recipe subscribes to that state to format status text and releases subscriptions during teardown. The component owns data-view policy; the application owns this display formatting.

## API

Data Table is workspace source. There is no public `proto-ui add` target. Passing `sortKey`, `sortDirection`, `page`, or `selectedKeys` selects controlled mode for that fact.

<ApiPropsTable
  headers={{ name: 'Prop', type: 'Type', default: 'Default' }}
  rows={[
    { name: 'rows', type: 'readonly DataRecord[]', default: '[]' },
    { name: 'defaultSortKey', type: 'string', default: "''" },
    { name: 'defaultSortDirection', type: "'none' | 'ascending' | 'descending'", default: 'none' },
    { name: 'filter', type: 'string', default: "''" },
    { name: 'columnFilters', type: 'Readonly<Record<string, string>>', default: '{}' },
    { name: 'columnVisibility', type: 'Readonly<Record<string, boolean>>', default: '{}' },
    { name: 'defaultPage', type: 'number', default: '0' },
    { name: 'pageSize', type: 'number', default: '10' },
    { name: 'defaultSelectedKeys', type: 'readonly string[]', default: '[]' },
    { name: 'disabled', type: 'boolean', default: 'false' },
    { name: 'readOnly', type: 'boolean', default: 'false' },
  ]}
/>

These props belong to Root. Row defaults `index` to `0` and `header` to `false`. Cell defaults `columnKey` to `''` and `renderValue` to `true`. Header defaults `sortable` to `true`. Previous and Next accept the Button props.
