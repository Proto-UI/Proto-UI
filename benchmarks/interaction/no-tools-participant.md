# No-tools participant exchange candidate

This is a **candidate client-side capability boundary**, not admission of real runs, arbitrary agents, secure provider internals or evaluator execution. It does not enable the historical benchmark `run` command. The library does not select or authorize a live paid route; a separately authorized coordinator can inject one. Credentials must not be copied into packets or evidence. Exploratory real-response collection does not admit the candidate oracle or the historical runner.

`participant/no-tools.mjs` serializes only an explicit prompt and digest-bound material allowlist to a stateless Responses-style request. There are no tools, MCP servers, file attachments, previous response IDs, repository paths, system configuration or chat history in the request. A trusted coordinator supplies transport/auth separately. Output is retained text, never evaluated as JavaScript or dispatched as a command; unexpected function/tool outputs fail closed with the raw response preserved. No automatic retry or repair feedback is permitted.

The enforced **client-side** boundary is that the remote text participant has no filesystem/Git/tool API exposed by this client. The coordinator can read local files and must remain trusted; whitelisted material authoring/digest approval is separate from isolation. This is not equivalent to running Codex `workspace-write` or a native subagent in a shared worktree. It cannot prove the provider has no server-side behavior, model pretraining exposure, retention, or side channels. Those limitations apply even when `tools: []`, `tool_choice: none`, and `store: false` are requested. Requested controls are not described as verified effective provider controls.

Tests exercise a real local HTTP boundary with evaluator canary bytes withheld, malicious read/exec instructions returned inertly, attempted function/computer/ search/MCP requests rejected, digest tampering and extra packet metadata rejected, and a wall deadline with no retry. These are **synthetic transport tests**, not model evidence. They do not make a public task held-out. A timeout asks transport to abort and stops waiting; a custom transport that ignores the signal can continue in the coordinator. A live transport must implement cancellation and bounded raw response reads before admission.

Receipts distinguish requested vs returned model names; an echoed name is not an immutable snapshot. Missing usage, seed, supported control details and billing remain unavailable/unverified, not zero. A token limit alone does not establish a cost limit. Provider-specific validation, independent review, exact frozen packets, bounded archives, browser/evaluator deadline, current-user billing authorization and per-cell/whole-attempt budgets remain gates before real Round0.

Collection: `pnpm benchmark:test`; focused: `node --test scripts/benchmark/participant/no-tools.test.mjs`.

## Bounded HTTP attempt archive (candidate)

`responsesTransport` in `scripts/benchmark/participant/http-transport.mjs` can be injected into `exchange`. It does not choose a provider, read credentials, infer a budget, or invoke a live route by itself. Use only after explicit channel/budget authorization. Plain HTTP requires explicit opt-in and a literal loopback address for local probes; otherwise HTTPS is required. Credentials in URL fields are rejected. Credentials belong in the trusted caller's bearer header, not packets or archive metadata. This boundary does not prove provider-internal isolation or eliminate training-data contamination.

Each transport is single-use and requires an exclusively created absolute archive directory (parent must already exist). It makes one POST, does not follow redirects, and does not retry. Whole-attempt and exchange deadlines, response byte limits and AbortSignal are separate controls. Store `request.json`, `response.raw` and `transport.json`, including hashes and exact success/error status. HTTP failure, invalid UTF-8/JSON, refusal and incomplete responses are not deleted. Oversize retains only a bounded prefix with `rawBodyComplete: false` and the observed byte count, never a falsely complete raw response. A response-received transport result does not establish a valid participant deliverable.

Trusted authorization headers are not archived, but provider raw bytes are untrusted and may themselves contain sensitive or malicious text. Keep archives private; do not execute participant output or automatically upload evidence. Filesystem archive errors are failures, not successful preservation. `exchange` records a transport evidence pointer: a deadline race may return while archive finalization is still `writing`; verify final `transport.json` before admission. Unknown usage, cost, immutable model snapshot and provider controls remain unavailable rather than zero or inferred. All transport tests are local synthetic servers, not real-model runs.

## Explicit streaming protocol

Requests default to `stream: false`. A coordinator may explicitly set the boolean `stream: true`; the plan, exact wire bytes and exchange receipt bind this choice. Streaming changes transport encoding, not participant task/material bytes, capabilities or authorization. The bounded HTTP transport retains original SSE bytes. The trust-repair decoder validates complete typed lifecycle events, item/content inventory, sequence, response identity and text agreement. Completed assistant `output_item.done` content supplies deliverable text; deltas are integrity checks, never the answer source. A nonempty terminal output must match assembled items. Empty terminal output may be normalized only after strict integrity validation, with the raw terminal and assembly provenance archived separately. Legacy terminal-only streams require explicit `allowLegacyTerminalOnly`; a malformed lifecycle stream never falls back to compatibility. Malformed or missing/duplicate terminal events are protocol failures. Byte limits, whole-attempt deadlines, aborts, no client retry and exclusive archive creation apply in both modes. Gateway retries are outside this client and must be reported separately when known.

A diagnosed setup failure may justify a separately versioned controlled rerun, with the changed protocol, same task bytes, fresh isolated requests and a new predeclared bound. This is not an automatic retry or answer-selection policy. The failed dispatch, unknown bill and total client dispatch count must remain in combined accounting; do not overwrite its archive.
