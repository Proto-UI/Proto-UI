# Proposed semantic-oracle follow-up

This is a plan, not a new oracle or task admission. Keep existing public calibration cases, oracle versions and archives unchanged. Any later expectation changes require a separately versioned oracle and independent review.

1. Map each public task clause to three separate judgments: public platform authority, independently reviewed black-box journey, and applicable Proto criteria. Record exact sections, applicability, lifecycle, revision, retained source bytes/digest and review disposition. Freeze the HTML/ARIA references already linked by `cases/*.json`, distinguishing normative platform requirements from APG authoring guidance. Bind browser/build, host, input method and tool versions. The dataset's `f5bae261491368b586959f1d8b353cf372775221` semantic baseline is distinct from a later checkout; newer Tabs relationship criteria must not silently alter it.
2. Locate unique targets by scoped accessible role/name, native label associations and actual control/panel relationships. Use IDs to resolve relationships, never to require `#fixture`, `#reference-dialog` or `tab-*` conventions. Compare actual focused elements during trusted navigation and reacquire semantic targets after rematerialization. Verify removal and subsequent keyboard navigation through the named task controls.
3. Resolve scope disagreements before implementation. Dialog's task describes a modal while the current calibration metadata/checks require native `<dialog>` and `:modal`; decide applicability explicitly before evaluating alternative implementations. Tabs' four permanent panel elements are a fixture choice; `P-BASE-TABS-CONTENT-DEFAULT-L1-DETACH` permits absent inactive views, while the task's reciprocal relationship clause still needs a reviewed interpretation. Preserve the task's manual activation and explicit wrapping; `P-BASE-TABS-LIST-PROP-LOOP` does not make wrapping a Base default.
4. Add public positive alternatives with randomized IDs, wrappers, equivalent valid names/labels, permitted negative tabindex values and the existing native-disabled/tabindex-zero variant. After scope review, include permitted modal/panel materialization structures. Pair them with targeted negatives for decoy/duplicate controls, missing names, dangling/cross-component relationships, escaped focus, navigation that selects accidentally, disabled-item activation, extra visible panels, stale output and broken cleanup. Verify the intended failure and unaffected observations, not merely a nonzero overall exit.
5. Keep the current native Select task native: it commits during keyboard navigation. `spec/prototypes/P-BASE-SELECT.yaml`, `P-BASE-SELECT-CONTENT.yaml` and `P-BASE-SELECT-ITEM.yaml` describe a popup scope with distinct navigation and selection. A popup case needs separate task design and authority; no parity is inferred from the native task.

Relevant source paths are `benchmarks/interaction/cases/*.json`, `scripts/benchmark/browser-calibration.mjs`, its browser tests, and `spec/prototypes/P-BASE-{DIALOG,TABS,SELECT}*.yaml`. Apply `scoring.json` conflict policy per layer: disputed/ambiguous claims require independent adjudication; unsupported host capabilities, blocked execution/evidence and untested checks remain distinct. No layer automatically overrides another, no public case becomes held-out, and none of this plan enables a model run.
