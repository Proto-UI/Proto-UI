## 1. 背景与问题

maintainer（广亮）在 #375 中整理了一份 0.3 原型扩充的市场比较基线与分类建议，并要求共同决策者（ezra）亲眼过目、补充判断，尤其是 Brutalist 方向，之后再由 AI 调研并发 Issue。

#375 本身的分类方向大体合理：它区分了 semantic primitive、styled projection、composition 和 application system，没有把 shadcn 的 64 项直接换算成 64 个 Base 原型。但它有三个风险：

1. **Brutalist 没有自己的产品方向**。#375 几乎只规划 Base 与 shadcn，Brutalist 容易退化为 shadcn 的镜像或附属品。
2. **"Base 30–35 个"和"shadcn 63/64"即使写成规划指标，也容易逐渐变成凑数 KPI**。
3. **maintainer 打算"按列表提及的所有原型让 AI 调研并发 Issue"**，如果按字面执行，会生成大量低质量 Issue，与 #375 自己"先建 Coverage Matrix、再发约 10–12 个语义切片"的建议矛盾。

本设计是对这三个风险的正式治理回应。

| Grill | 问题 | 确认结果 |

## 3. 治理结构：三账本一矩阵

### 3.1 总 Coverage Matrix

每一行代表一个市场目录项或 Proto UI 自主候选，至少记录：

- 候选名称与快照来源（2026-08-13 冻结）；
- 实际身份：semantic / projection / styled-only / composition / provider / system / excluded；
- Base、shadcn、Brutalist 三条线分别如何处置；
- 前置 prototype、module、host-cap、test；
- owner、难度、目标波次、当前状态；
- 已有证据与仍待调研问题。

**0.3 的覆盖完成条件：矩阵中的全部范围得到人工确认的分类。** 这不表示所有行都已实现，更不表示每行对应一个同名 prototype。

### 3.2 Base 语义账本

只收录拥有独立、可测试、跨宿主信息路径的语义协议。

准入门槛（三项全满足）：

1. **独立信息路径**：拥有可测试、跨宿主的状态、事件或可访问性通道。anatomy 名、空 props、源文件、`asHook` 入口都不是协议。
2. **module/host-cap 就绪**：所需底层能力已 active 或 draft 阶段已明确边界。不能在 prototype 内隐式发明宿主能力。
3. **无更简单归属**：如果候选只是现有协议的组合或视觉投影，就不应新建独立 Base。复用现有家族不等于自动形成新的协议身份。

### 3.3 shadcn 处置账本

目标是解释 64 个目录项，而不是复制 64 套 API。每项只能归入：

- existing（已覆盖）；
- Base 的 shadcn projection；
- 新 semantic prototype；
- composition/recipe；
- provider/system mapping；
- excluded。

Composition 不冒充独立 semantic primitive。`63 + 1 = 64` 是覆盖分类，不是包、导出或 spec prototype entity 的强制数量。

### 3.4 Brutalist 双轨账本

明确分成两列，避免身份混淆：

**第 1 轨 — Semantic projection**

- 消费已成立的 Base 协议；
- 该协议必须存在可观察、可设计的宿主表面；
- 负责 Brutalist 视觉语法，不重定义语义；
- 例如 Button、Dialog，以及 Base Radio Group 合入后的视觉投影。

**第 2 轨 — Direct styled-only**

- 不虚构 Base carrier；
- 必须有稳定、可复用、可测试的视觉合同；
- 至少在两种真实组合中成立；
- 不能只是"一串方便复用的 class"；
- 例如已经成立的 Badge、Card、Skeleton。

三本账可以互相关联，但不互相冒充。尤其不能因为 shadcn 有某个名字，就同时制造同名 Base 和 Brutalist prototype。

## 4. 准入门槛与分类规则

### 4.1 分类规则示例

| 候选 | Base | shadcn | Brutalist | 理由 |
|---|---|---|---|---|
| Card | 不建 Base | styled-only | styled-only | 有可独立测试的视觉结构，不虚构交互协议 |
| Typography | 不建 Base | shared style / content | shared style / content | 无独立 anatomy 或信息路径 |
| Data Table | 不建同名 Base | composition | composition | 组合 Table、Collection、Selection 与 Pagination |
| Table | **Base 结构语义** | 投影 | 投影 | 拥有跨宿主表格结构与可访问性关系，不拥有排序、选择或分页 |
| Tooltip | Base owns | 投影 | 投影 | Base 拥有语义；Arrow 仅在有独立信息路径时才成立 |
| Avatar | 等 Image Base 研究完成 | 投影候选 | 投影候选 | 不先假定一个 styled-only Avatar；Image→Avatar 依赖仍需对应切片验证 |

### 4.2 一个关键判断

- 有人会因为 shadcn 有 `DataTable` 而想在 Base 里建 `BaseDataTable`。**不应建**。Data Table 是 composition，不是 semantic primitive。
- 有人会因为 shadcn 有 `Typography` 而想在 Base 或 Brutalist 里建 prototype。**不应建**。Typography 是散布于内容槽与设计系统 projection 的 shared style，不是 prototype。
- 有人会因为 shadcn 有 `Avatar` 而想立即做 Brutalist styled-only Avatar。**不应先行准入**。应先通过 Image→Avatar 语义切片验证媒体生命周期、fallback 与视觉表面的所有权。

## 5. Brutalist 双轨候选集

### 5.1 第 1 轨 — Semantic projection（消费已成立的 Base）

| 候选 | 当前判断 | 说明 |
|---|---|---|
| Checkbox | 应投影 | 复用 Checkbox Base，补充明确的 Brutalist control/indicator 视觉表面 |
| Tooltip | 应投影 | 复用 Tooltip Base，定义 Brutalist 内容表面、边框与偏移视觉语法 |
| Radio Group | 待 Base 合入后投影 | #349 的语义 checkpoint 已批准；必须等 Base 实现合入，不将工作分支当作现状 |
| Transition | 不单独投影 | 没有独立可见表面；由实际 styled prototype 使用 Base Transition |
| Live Region | 默认不投影 | 可访问性协议本身不构成 Brutalist 视觉表面 |
| Async Region | 默认不投影 | 异步边界协议本身不构成 Brutalist 视觉表面 |

成熟 Base 只是投影的必要条件。Brutalist 不为没有独立视觉表面的 Base 家族制造薄包装。

### 5.2 第 2 轨 — Direct styled-only 调研候选

下表是 research queue，不是准入结果。每个候选都必须先提供至少两种真实组合、精确视觉合同、非目标和可执行证据，之后才能由 Brutalist 领域共同负责人签字进入实施 Issue。

| 候选 | 调研重点 |
|---|---|
| Alert | 验证稳定 visual anatomy 与 tone 是否成立，并明确被动 Alert surface 不拥有 Live Region 或 Toast 的动态公告语义 |
| Spinner | 验证可复用视觉/动效合同；busy、loading 与 announcement 仍由父级异步边界拥有 |
| Kbd | 验证键帽展示语法是否形成独立 anatomy/API，而不只是一个共享 class |

当前不进入该调研队列：

- Avatar：先走 Image→Avatar 语义依赖研究；
- Typography：作为 shared style/content 处理；
- Empty / Placeholder：当前证据只支持内容组合；
- Item / Breadcrumb：当前证据只支持组合或结构组件；
- Button Group：先作为 Button/Toggle/Toolbar 组合问题研究；
- Table：已进入 Base 结构语义账本，不走 styled-only。

### 5.3 Brutalist 现有覆盖快照

当前已导出的 Brutalist 家族：

- Semantic projection：Button、Toggle、Switch、Tabs、HoverCard、Dropdown、Select、Dialog、ScrollArea、Textarea、Separator
- Direct styled-only：Skeleton、Badge、Card

## 6. Issue 发布顺序

替代 maintainer"按所有名字跑一圈调研并发 Issue"的执行方式。

| 波次 | 内容 | 为什么这样排 |
|---|---|---|
| W0 | 在 #375 合入前确认并补入本治理修改；随后建立总 Coverage Matrix | 避免先合入旧方向、再用第二份 record 纠偏 |
| W1 | 补齐各账本真实缺口：shadcn 的 Checkbox/Scroll Area/Separator/Textarea/Tooltip；Brutalist 的 Checkbox/Tooltip | 只补尚不存在且具有视觉表面的投影 |
| W2 | 调研 Brutalist styled-only 第一批候选（Alert、Spinner、Kbd） | 调研通过准入门槛并共同签字后才发实施 Issue |
| W3 | Image→Avatar、Radio Group（#349 checkpoint 已批准） | 先完成并合入 Base，再建立设计投影 |
| W4 | Disclosure→Accordion、Input/Label/Field/Native Select、Table（Base 结构语义） | 先锁定语义边界与依赖；Table 不隐式吸收排序、选择或分页 |
| W5 | Popover、Progress、Slider、Toast、Toggle Group | 只有相关 overlay/positioning/move-gesture 能力边界足够明确后才推进 |
| W6 | C 组高级交互 | 在相关 module/host-cap 编目完成后单独拆 |

### 6.1 Issue 发布规则

1. 在 #375 合入前确认其分类框架与本治理修改；
2. 建总控 Coverage Matrix Issue；
3. Brutalist 领域共同负责人补充/修正 Brutalist 身份、视觉合同与复杂度判断；
4. 第一批只发布经过人工确认的语义切片、真实投影缺口和通过准入的 styled-only 任务；总量控制在约 10–12 个 Issue；
5. 每个高级语义 Issue 都先写依赖与边界，不能直接进入实现；
6. C 组 Issue 必须列出前置 spec entity；若依赖实体尚为不完整 draft，应先完成其编目；
7. 不按全部 64 个组件名称逐个发 Issue。

### 6.2 难度标注

- 纯设计投影且 Base 语义已稳定：可供一般贡献者承接；
- 新 Base semantic slice：至少 maintainer-guided；
- 会改变 module、host-cap 或跨宿主协议：仅建议核心贡献者或组织成员承接。

## 7. 0.3 建议验收口径

在不把本文提升为规范承诺的前提下，0.3 的路线图验收口径是：

- 冻结快照中的 64 个 shadcn 条目全部得到人工确认的唯一主分类与明确去向；
- 已实现、延期、composition/provider/system mapping 与 excluded 必须分开报告，不能合并成一个“覆盖数量”；
- 实际交付的组件数量作为版本快照报告，不是 release gate；不以 51、63 或任何滚动目录数量强迫实现薄投影；
- Chart 在 2026-08-13 快照中保持唯一明确排除项；后续目录变化不自动改变 0.3 范围；
- Base 30–35 个家族仅作市场量级观察，不是准入或 release gate；
- Brutalist 第 1 轨只投影同时满足“Base 已成熟”与“存在可设计宿主表面”的家族；第 2 轨 styled-only 只收录通过视觉合同门槛并获得共同签字的候选；
- 新 B/C 原型的 Issue 必须记录 module、host-cap、test 与 adapter 依赖；
- Adapter 扩充继续等待 Adapter、modules、host-cap 第一轮 spec 编目完成。

覆盖分类闭环不等于实现闭环。

## 8. 非目标

- 不定义任何新原型的稳定 props、events、states 或 anatomy（那是各语义切片 Issue 的工作）；
- 不修改现有 spec entity 的生命周期或版本范围；
- 不承诺 0.3 的发布日期；
- 不决定各平台 Adapter 的实现顺序；
- 不承诺 Chart、可视化引擎或第三方图表库集成；
- 不把 shadcn 页面数量等同于 Proto UI 的长期产品规模。

## 9. 对 #375 的具体修改建议

本设计不否定 #375 的分类框架，而是在其上追加治理层：
1. **追加 Brutalist 双轨账本**，补齐 #375 缺失的 Brutalist 产品方向；
2. **将“Base 30–35”“51 项正式组件”和“63/64”明确为观测或分类数据，而非强制实现阈值**；
3. **将 Issue 发布方式明确为“先建 Matrix、再发经人工确认的切片”，禁止按 64 个名称机械逐项发 Issue**；
4. **追加 Base Table 只拥有结构与可访问性关系的边界**；排序、选择与分页属于 Data Table composition；
5. **追加 Brutalist 投影必须具有可设计宿主表面的准入规则**；
6. **追加 Brutalist 领域共同签字机制**。

建议在 #375 合入前直接修订其 record；若 maintainer 希望保留原提案历史，则在同一 PR 中追加一份明确更新它的较新 record，而不是合入后长期保留两个竞争方向。
