# v0.3 Prototype Issue Publication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Amend #375 before merge, establish one authoritative v0.3 Coverage Matrix, and publish a bounded first tranche of independently actionable proposal, implementation, projection, and research Issues without mapping all 64 shadcn names mechanically to Issues.

**Architecture:** Use four Issue kinds with explicit lifecycle transitions: tracking, semantic proposal, approved implementation, and design-language projection/research. One tracking Issue owns coverage classification; each implementation Issue owns one mergeable semantic family. Existing #349 transitions to a linked Base Radio Group implementation Issue; #374 remains the Image proposal until its semantic checkpoint. Brutalist admissions require domain co-signoff.

**Tech Stack:** GitHub Issues/labels/sub-issues, Proto UI `spec/**` authority model, #375 roadmap record, issue templates under `.github/ISSUE_TEMPLATE/`.

---

## Publication invariant

Do not create one Issue per shadcn directory name. The first tranche contains eleven new Issues plus existing #374; #349 closes only after its approved implementation follow-up exists. Later Issues are created when their dependency gates open.

Every Issue must declare exactly one primary kind:

- `tracking`: owns status and links, no implementation contract;
- `proposal`: resolves an unsettled semantic or admission boundary and ends at a maintainer checkpoint;
- `implementation`: realizes an already approved contract and ends at a merged PR;
- `projection`: applies an existing Base contract to one design language without changing Base semantics.

A proposal must not silently become an implementation Issue. At checkpoint approval, open a linked implementation Issue, record the approved boundary, then close the proposal.
