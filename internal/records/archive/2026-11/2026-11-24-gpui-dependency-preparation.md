# GPUI dependency migration preparation — 2026-11-24

## Scope and decision

The user asked to prepare Proto-UI Compiler for moving away from its old commit-anchored GPUI dependency after Zed announced an independent repository and an upcoming registry release. This record covers preparation on baseline `b939afe35d30a1a436766d80beea7093a46e4fb2`; the [migration guide](https://github.com/Proto-UI/Proto-UI/blob/df54e9b7bb8f5cd8a110dfff1ab42980242dea5d/internal/compiler/gpui-dependency-migration.md) retains the observed upstream and consumer identities and owns the future activation checklist.

The default remains `zed-industries/zed@62e5991dd0f0c8a3af8d5e7e9c4652490d468db8`. At observation time the independent repository had only a README, while the existing registry `gpui@0.2.2` was an older release. No new release, API capability, lifecycle promotion, or native acceptance is claimed.

The preparation centralizes the default source, permits explicit Git or exact registry identities in the resolved-graph gate, and checks `gpui_platform` independently. Existing Git callers remain supported. Compiler, SDK, fixture producers and workflow commands consume the same default declaration. Registry versions are complete versions rather than ranges; platform versions are not inferred from GPUI versions.

## Failures retained and corrections

These are internal build/tooling observations. The table identifies the measured divergence and its owner; no synthetic UI image or native-input claim is used.

| Case | Trigger and observed values | Correction and recheck |
| --- | --- | --- |
| Existing producer duplicate | The ordinary-values producer registered `external_scroll` once through real file compilation and once again through `emit`; Cargo rejected the resulting duplicate dependency key | Keep the real file/import compilation path, remove the second registration, and reject duplicate module names before writing artifacts. The [initial failing run](https://github.com/Proto-UI/Proto-UI/blob/cae25ae39f926e9556ec40fe2c7ed46a2025091f/internal/records/evidence/2026-11-24-gpui-dependency-preparation/cargo-graph-tests-initial.log.gz) and final passing manifest test are retained |
| Review R1: fixture target ownership | CI supplies an external `CARGO_TARGET_DIR`. `cargo package` wrote there, while the new fixture read `<fixture>/target/package`; the archive lookup failed with ENOENT | Give every fixture Cargo process its private target and assert the actual metadata target directory using physical paths. The [independent red result](https://github.com/Proto-UI/Proto-UI/blob/cae25ae39f926e9556ec40fe2c7ed46a2025091f/internal/records/evidence/2026-11-24-gpui-dependency-preparation/independent-ci-target-red.log), full run and isolated subset retain the transition |
| Review R2: registry configuration lookup | For the same consumer manifest and lockfile, invocation from the consumer directory passed; invocation from the Compiler root failed with Cargo 101 because the named registry configuration was undiscovered | Resolve manifest/output paths against the caller first, then run Cargo from the manifest directory. The receipt records `cwd`. New real Cargo cases check caller-relative paths and workspace ancestor configuration; the [independent before/after report](https://github.com/Proto-UI/Proto-UI/blob/cae25ae39f926e9556ec40fe2c7ed46a2025091f/internal/records/evidence/2026-11-24-gpui-dependency-preparation/registry-cwd-review.json) retains the control |

The first isolation diagnostic required the entire externally supplied target to stay empty during both test files. That was too broad: an existing Git test writes only `.rustc_info.json` there. Its [failed diagnostic](https://github.com/Proto-UI/Proto-UI/blob/cae25ae39f926e9556ec40fe2c7ed46a2025091f/internal/records/evidence/2026-11-24-gpui-dependency-preparation/target-isolation-first-diagnostic.json) is retained. The complete run now checks absence of fixture artifacts; the new registry file is also run separately and does leave the external directory entirely empty. This does not erase the original R1 failure or weaken its archive-location assertion.

## Review and follow-up

An independent read-only source review reproduced R1 and R2 before correction and reran their real Cargo controls. Its [report](https://github.com/Proto-UI/Proto-UI/blob/cae25ae39f926e9556ec40fe2c7ed46a2025091f/internal/records/evidence/2026-11-24-gpui-dependency-preparation/independent-review.md) records the final disposition and limitations. This local source review is not a GitHub `APPROVED` review or permission to merge. Publication and integration must retain the actual head, DCO, checks and required independent platform review.

The preparatory criterion is distinct from adoption. The future source must first exist as a usable crate/release. Then validate its actual API, feature and toolchain surface; regenerate source and lockfiles; execute native and platform acceptance; update Verdant's fork-aware pin/schema producer and fresh receipts; and run Shenko's React Compiler regression. The [activation and rollback checklists](https://github.com/Proto-UI/Proto-UI/blob/df54e9b7bb8f5cd8a110dfff1ab42980242dea5d/internal/compiler/gpui-dependency-migration.md#future-activation-checklist) remain open. Verdant currently depends on a capability-bearing fork; Shenko is a non-GPUI consumer. Neither application's existing evidence certifies a future GPUI source.

No new-source native build, three-platform application build, actual window/input/accessibility journey, package release, default dependency switch, or repository-wide integration cycle was run for this preparation. Those are explicit later obligations, not skipped tests counted as passes.
