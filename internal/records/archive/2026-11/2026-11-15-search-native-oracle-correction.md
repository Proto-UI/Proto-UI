# Search native evidence oracle corrections

Date: 2026-11-15. Scope: the existing production Search IME, Homepage late-publication rollback, and short-viewport nested-scroll journeys. This record does not promote a prototype lifecycle or claim physical OS IME, assistive-technology, or full release acceptance.

## Independent native IME control

The original production test required `compositionend.isTrusted === true` after the runner sent `Input.imeSetComposition` followed by `Input.insertText`. Both Shadcn and Brutalist reached the committed `Button` value and received real Pagefind result fragments, but failed this event-trust assertion within its original 1000 ms poll.

An independent, normal-sandbox Chrome 157.0.8103.38 control containing only an HTML `input` reproduced the same event sequence without Proto, adapters or website code. Its composition start, updates and composing input events were trusted. Its composition end was untrusted. Native Tab, pointer blur and an empty composition cancellation also produced an untrusted end; Enter alone did not finish the composition. The original observations are retained in `web-acceptance/plain-input-ime-cdp.json` and `web-acceptance/plain-input-ime-commit-controls.json` under the continuation evidence root.

The corrected test obtains a fresh independent control in the same browser process on every production run. The actual Search trace must match that control's event order, trust bits, composing flags, input types, data, values and selection boundaries. The end trust bit is preserved and compared exactly; the test does not generally accept either trust value. A separate `dispatchEvent`-only forgery on the empty control page must be rejected because its native editing prefix is untrusted. Focused negative cases also reject a forged start, update, beforeinput or input and an incomplete composition.

The original 1000 ms commit poll remains. Existing live-editor identity, asynchronous selection retention, composition-time result suppression, final query, genuine generated Pagefind results and keyboard navigation checks remain. This is browser-host IME evidence driven by CDP, rather than physical OS IME or assistive-technology evidence. `native-ime-plain-input-control.json` records the independent control and negative control alongside each production run.

## Homepage rollback clock

The three existing late-publication tests injected their fault only after replacement activation. However, their default 1000 ms error-state poll began at the earlier cold framework-switch request. The successful Homepage switch helper separately waits for framework readiness. These are different observation boundaries.

The original normal-sandbox baseline recorded request-to-fault intervals of 1649.5, 1627.7 and 1637.2 ms. Fault-to-first-observed-error intervals were 501.8, 474.7 and 488.5 ms. Adding the initial Input/Select/Collection candidate did not remove the preparation cost: request-to-fault remained 1868.1, 1698.9 and 1571.7 ms, while recovery took 481.5, 528.0 and 510.0 ms. Both runs preserve three failed tests and 80 filtered tests; neither is called a pass.

The corrected oracle waits for the required publication fault using the same readiness mechanism as a successful framework switch. It then retains the error-state poll and independently requires `firstErrorAt - faultAt <= 1000` using one page `performance.now()` clock. A late Node-side observation cannot restart or erase that budget. Missing, nonfinite or reversed timestamps fail. The same retained generation, panel/editor identity, query, selection, session-open state and eligible or newer focus checks still follow. A separate opt-in CPU profile records expensive preparation without changing the ordinary run.

The test boundary changed explicitly: 1000 ms now constrains recovery from the actual injected publication fault, while framework preparation has its existing readiness boundary. It is not evidence that cold full-page framework replacement takes less than one second.

## Search viewport and oversized rows

The first integrated native run retained all eight nested-scroll failures. Read-only native diagnostics confirmed that the actual served Search source included `__revealActive`, the live Content exposed it, and the new Scroll host implementation was loaded. At 320 × 390 with a 200% root font, the Shadcn outer scroll body was 56.5 px tall and the Brutalist body was 94 px tall. A 104 px nonshrinking status/actions block consumed the available flex space, leaving both Content viewports at zero height. The host correctly rejected an unavailable viewport; it made no `scrollTop` write. The raw receipt is `web-acceptance/scroll-native-diagnosis.json`.

The website layout now gives Content its natural content height capped by `max-height: 100%`, without shrinking it behind the wrapped status/actions block. Overflowing status/actions remain in the outer body scrollport; dismissal stays outside it. A diagnostic CSS-only control restored Content to 40.5 px in Shadcn and 94 px in Brutalist, with outer body scroll ranges still available. It also exposed a separate host precision defect: treating the rounded integer `offsetHeight` of 41 as an exact denominator for a 40.5 px box caused approximately 64 px of accumulated overscroll over a long result list. This is a product geometry defect, separate from the test oracle. The parent Scroll change fixes fractional box measurement and retains real transform-scale handling. The CSS-only diagnostic remains marked diagnostic, not acceptance: `scroll-flex-none-native-diagnosis.json`.

The original test required the whole last-row rectangle inside the outer body. Its measured row heights were 290 px and 184 px, both taller than those body viewports. Full containment was impossible. Under `C-SCROLL-TARGET-REVEAL-0001-HOST`, the corrected test uses the actual Content viewport, including scroll padding and the target's scroll margin. Ordinary rows must still fit completely. Oversized rows must intersect the viewport and align the nearest edge within the original 1 px geometric tolerance. A negative control rejects the observed 64 px overscroll even though that row still intersects the viewport.

The native journey measures before/after bounds, positive viewport height, input focus, all ancestor scroll positions and stable repeated boundary keys. It also exercises ordinary rows at 100% in the same live composition before restoring 200% for the original touch, failure/retry, loading, empty and dismissal steps. The actual native receipts are saved before assertions so a failure does not erase its geometry. These are explicit oracle changes and additional checks, not a claim that the original impossible containment assertion passed.

The v2 native run passed the 200% End/Home geometry checks in all eight family/host combinations, including the unchanged focus and ancestor positions. It still failed all eight complete nested-scroll cases: after changing the same page to 100%, a stationary pointer received `pointerenter` as the list moved under it. The Search item handler then replaced the keyboard-selected last row with row 17 in Shadcn and row 16 in Brutalist. Public input state remained focused, not composing, enabled and expanded, with the same input, query, Content, root and panel identities. An independent fresh 100% fixture worked; moving the mouse away only as a diagnostic control also restored the expected last row. This is a genuine pointer-intent implementation defect. The actual native journey keeps the original pointer coordinates; it does not move the pointer away to pass. The complete trace is `search-scroll-resize-native-diagnosis.json`.

Visual review then found a remaining consumer layout defect even with a positive Content height. The earlier CSS-only screenshots `scroll-flex-none-diagnostic-shadcn.png` and `scroll-flex-none-diagnostic-brutalist.png` show the wrapped keyboard hint consuming the fixed footer: Shadcn's 40.5 px Content has only 12.5 px of effective space after scroll padding, leaving a horizontal text sliver instead of a readable title. These are historical diagnostic screenshots with the older host precision implementation, not screenshots of the later v5 manifest. Their Content and footer layout matches v5, and the geometry independently proves that a complete title line cannot fit. The two-family/four-host consumer regression produced eight failures and 17 passing controls against that fixed-footer layout, with zero skips (`search-footer-layout-red.json`).

The consumer now places the noninteractive keyboard hint alongside status/actions in the outer scroll body, outside the listbox. The fixed dismissal contains only the actual Dialog.Close. The native journey additionally requires the first rendered title line to fit after End, records selected results at both 200% and 100%, and reaches the hint with real wheel input only after all original keyboard/pointer-coordinate checks. It retains the fixed Close hit checks, input focus, unchanged keyboard-driven ancestor positions, ordinary-row containment and the existing timing budgets. The four focused suites passed 95/95 with zero skips after this layout change (`search-footer-layout-green.json`); actual native readability and interaction acceptance remain separate.

## Genuine empty Pagefind query

The v2 production run reached and passed both exact native IME-control comparisons. Its two IME journeys then failed the later empty-result assertion within the unchanged 20 s budget. The fixture query `zxqv948271605emptycontract` was not empty in the generated index: a separate plain zh-CN HTML page imported the actual Pagefind bundle and returned three genuine pages (the Lucide icon index, Lucide overview and quick-start page), without any Proto or Search consumer code. Those are the same pages rendered by the failed Search journey. The ordinary query `Button` returned 92 pages in that independent control.

The replacement query `qzxvjkphnwmrgqztvxknqjpl` returned zero results from that same index. The production suite now records a fresh independent control on every run, requiring the replacement query to have zero hits and `Button` to have positive hits before exercising Search. It also records the old query's actual count without fixing that count as a requirement. The control receipt is `pagefind-empty-query-control.json`. UI empty-state text, removal of stale options, editor identity, keyboard execution and existing timeouts remain. This corrects fixture data; it does not change Pagefind behavior or accept unexpected Search results.

The same v2 production run still failed both ordinary runtime-change 1000 ms polls. A separate diagnostic measured cold Shadcn Vue→React readiness at 1083.2 ms and Brutalist at 428.4 ms, which is insufficient to explain both original failures. The original production dispatch now records request and committed-ready observations on the same page clock, including failure capture, while preserving its 1000 ms assertion. No runtime-switch budget has been changed on the strength of this partial diagnosis.

The original 83-case baseline also failed `homepage brutalist/react mobile keeps the Search trigger centered through closed/open/reopen`. The captured closed Header had Search and Theme centers at 28 px while Menu's center was 30.7805576 px. The pointer was still over the family Menu Button, whose authored hover translation was in flight; the captured Menu y-coordinate was 8.7805576 px rather than its resting 6 px. ## v6 full native run and exact native range clamp

The unprofiled v6 run executed all 83 cases: 74 passed, nine failed, zero were skipped, and it exited 1 after 707.7735 s. All 70 source hashes in `web-final-native-v6-manifest.json` remained unchanged. The three rollback cases and the Header centering case passed. The nine remaining failures were all eight nested-scroll journeys at their 100% ordinary-row check and one Shadcn dark 390 px activation/dismissal focus poll. The exact result is `search-final-native-v6.json`; no complete nested-scroll case passed in that run.

All eight nested-scroll cases reached the 200% End/Home/repeat checks with the original pointer positions, unchanged input focus and ancestor scroll positions. The actual v6 WC screenshots `search-scroll-shadcn-wc-selected-200pct-nearest-edge.png` and `search-scroll-brutalist-wc-selected-200pct-nearest-edge.png` show the selected Result 19 first title line fully readable and the fixed Close visible. Shadcn Content was 90.5 px high with 62.5 px of effective space. The long result remained oversized; these captures do not prove full-row visibility or the later wheel-to-hint step, which was not reached.

At 100%, the selected ordinary Shadcn row was 70 px high, from y=251.5 to 321.5. Content's measured rectangle ended at y=321, its `clientHeight` was 211, `scrollHeight` was 1212 and `scrollTop` was exactly 1001, the native maximum. The preferred viewport ended at y=315 because of scroll padding. The physical row was fully inside the client viewport within the existing 1 px tolerance, but the additional 6.5 px preferred inset required scrolling beyond the native range. The other seven combinations failed at the same kind of range boundary.

The draft `C-SCROLL-TARGET-REVEAL-0001-HOST` explicitly combines nearest reveal with native range clamping. The oracle therefore continues to prefer full ordinary-row containment in the effective viewport, and admits an unavailable preferred inset only at the exact corresponding native min/max boundary. It separately requires the entire actual ordinary-row rectangle inside the physical client viewport within 1 px. An interior inset violation, a clamp in the opposite direction, a physically clipped row, invalid geometry and an oversized row with the wrong nearest edge are still rejected. The oversized-row rule and all timing budgets are unchanged. Against the old predicate, the two valid clamp controls failed while 45 other controls passed; the corrected predicate passed all 47 controls, with zero skips (`search-native-clamp-red.json`, `search-native-clamp-green.json`). This is an explicit oracle correction, not a claim that the old preferred-inset assertion passed or that new native acceptance is complete.

The v6 focus failure retains its original 1000 ms exception and final scene. Its earlier timeline observed focus return after about 46 ms, but it did not record the actual failing getter's execution or node identity. Final focus alone is insufficient to close that failure. The next candidate records each original getter's Node start, settle, value and exception; the same page callback records connected/current/initial element identity and active element. It keeps the original locator, focused predicate and poll budget, and records browser long tasks without adding a readiness wait.

## v6 production harness failure and measured runtime blocking

The v6 production runner exited 1 after 169.1684 s with two failed recovery cases, two skipped IME cases and one `beforeAll` failure. All 70 candidate source hashes remained unchanged. The independent native-input IME control ran, but the new independent Pagefind control did not: Vite's SSR transform rewrote the browser callback's dynamic import to an unavailable `__vite_ssr_dynamic_import__`. Consequently no v6 IME or empty-state acceptance is inferred from earlier v2 traces. The definitive log is `search-production-final-v6.log`, with its start, exit and cleanup receipts.

The independent Pagefind callback now owns its native browser import through a self-contained `Function('url', 'return import(url)')`, so Vite cannot substitute its server import helper. Two controls execute the actual transformed callback in an isolated context without Vite SSR globals, verify the exact Pagefind URL and options, and preserve index errors rather than reporting them as empty results. Together with the geometry and observation controls, the focused suite passed 49/49 with zero skips. The full four real production cases still require a fresh run.

Both original runtime-change gates remain 1000 ms with the same `site-search` attribute locator. The v6 ordinary page and Node clocks showed why a committed-ready marker was insufficient: Shadcn's marker arrived 722 ms after the original poll began, but its last attribute read took 4392 ms to return `react`; Brutalist's marker arrived after 413 ms and its last read took 3844 ms. The receipts are `shadcn-runtime-react-poll.json` and `brutalist-runtime-react-poll.json` under `production-final-v6/homepage-evidence/search-production`.

A separate opt-in Shadcn recovery diagnostic retained the original getter and gate and failed that one selected case, with three other cases filtered. It exited 1 after 159.2001 s and left all 71 manifest hashes unchanged (`web-runtime-profile-candidate-manifest.json`). Chrome recorded a 4343 ms main-thread long task beginning at page time 11084.2 ms, overlapping the ready marker and delayed getter. Node's observed event-loop maximum was 32.768 ms. The raw CPU profile attributes about 2794.5 ms to the dynamic projection's `setChildren` completion path; two nested `setSurfaceStyle` calls each incurred about 1.4 s through the React renderer's synchronous whole-tree update. The bundle frame is named `projection-materializer`, but the corresponding source is `PrototypePreviewer/projection-composition.ts`: it projects the current theme before committing children, then unconditionally reapplies the theme across all committed dynamic slots after completion. This is measured product work, not proof of a Playwright locator or transport defect. The source owner is repairing the redundant call path while retaining synchronous commit and theme-change behavior; the native gate remains unresolved until replayed without the profiler.

The raw profile, long tasks, Node histogram, original poll and derived frame summary are retained under `production-runtime-profile/homepage-evidence/search-production/shadcn-runtime-react-*`. Diagnostic instrumentation is identified separately from ordinary native acceptance; it does not replace the failed v6 runs or claim a release gate passed.
