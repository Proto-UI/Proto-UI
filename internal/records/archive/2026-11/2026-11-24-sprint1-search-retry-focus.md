# Sprint 1: preserve an unaccepted Search Retry focus handoff

The original [complete S1 run 45238345986](https://github.com/Proto-UI/Proto-UI/actions/runs/45238345986), on clean `81c103bd462b73910f7279122fab5f282d172d56`, executed all four production Search cases. Two failed the original 1,000 ms HEAD503 Retry-focus assertion; the two native IME cases passed. In both failed family captures the query was empty, the panel and Retry action were visible, and the query input still held focus. No runtime error was recorded. These native observations remain failures on that source.

A reduced public-control test exposed a concrete composition defect: `focusedFailureAction` was recorded before `focusSelf` had been accepted. A refusal before the panel focus scope activated was therefore consumed permanently. A subsequent legitimate paint skipped the same action. The panel transition callback retried generation-swap restoration but did not retry this initial failure handoff. Both new controls failed on the unchanged composition (28 pass / 2 fail / 0 pending).

The repair waits for the current panel's presentation fact, issues the existing public focus command, and records completion only when the current control reports `focused`. It rechecks live owner, active generation, open state, paint epoch, opening identity and action identity after that observable call. The panel's existing transition notifications request a normal paint; no polling timer, extra readiness budget or DOM-based focus shortcut is introduced. The original opening focus epoch and manual-entry policy continue to protect a later user choice.

The full modified composition-cost file passed 30/30. Independent lifecycle review then added three controls: no attempts while presentation is absent; synchronous disposal during the focus call; and action replacement plus reentrant paint during the call. The final file passes **33/33**, zero pending. Accepted focus is not repeated by later normal paints or duplicate transition notifications. Newer focus intent remains decisive even after the user returns to the query.
