## Current failures, responsibility and preserved assertions

The first run selected all thirteen files from the earlier foundation verification plan. It completed with **363 passing and eight failing tests, across eleven passing and two failing files**. Both failures had concrete, different causes.

**Calendar / Date Picker was a product ordering regression.** Calendar published `selectionCommit` before the corresponding `valueChange` callback. Date Picker consumed that completion and requested Popover closure before the callback could retire the current view. The original four normal/unmount/dispose/remount tests observed `openChange` before `valueChange`, including the cases that should suppress the old close entirely.

Calendar now publishes canonical selection independently from dependent completion. It publishes the matching completion only after the change callback has returned and the owner, view epoch and request identity still match. Synchronous controlled acceptance remains canonical; refusal, superseding requests, unmount and disposal do not acquire a stale completion. This implements the existing boundaries in `C-CALENDAR-SELECTION-0001`, active `C-LIFECYCLE-0008` and the draft [notification-completion explanation](../../../contracts/prototype-base/notification-completion.v0.md). No normative text or Date Picker-local workaround was added.

The original four assertions remain intact. Sixteen additional cases cover single/range × uncontrolled/controlled × normal/unmount/dispose/remount, including owner acceptance inside the same callback. Running those sixteen against the original Calendar implementation produced **16/16 expected failures**; the other 69 cases in that deliberately filtered negative run were unselected, not waived acceptance. The five affected Calendar/selection files then passed **133/133**.

**Number Field was a stale fixture premise.** The original fixture prepared `requestInput('2', true)` and immediately called `commitValue()`. Current behavior correctly refuses to commit while composition is active, so `valueChange` never occurred and the retirement observer stayed at zero. Removing that composition guard would regress input behavior.

The original named commit test now uses controlled `value: 1` and a noncomposing draft proposal `2`, whose owner has not accepted it. It asserts canonical value `1` and draft `'2'` before committing, and canonical value `1` when the change callback runs. A separate uncontrolled case uses `defaultValue: 1`, `allowEmpty: true` and an empty noncomposing draft: input leaves canonical `1`, while commit requests and accepts `null`. Both preserve the existing `observed === 1` and normal-versus-retired `valueCommit` counts. No Number Field implementation or composition assertion was removed.

After both repairs, the original thirteen-file selection plus the sixteen new Date Picker cases and four new uncontrolled Number Field cases passed **391/391, thirteen files**. The 133-case Calendar result and this 391-case result overlap in `selection-reset-lifecycle.test.ts`; they must not be added into an aggregate unique-case total. The original eight failures, new old-source negative control and passing reruns are separately retained in the JSON log manifest.
