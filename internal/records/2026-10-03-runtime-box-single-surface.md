# RuntimeBox: one app-owned canvas surface

The reported library overview placed a rounded preview inside a separately painted square Brutalist article. Source inspection confirmed three competing owners: `PrototypeLibraryOverview.astro` article paint and its explicit inner radius, `PrototypePreviewer.astro` / `runtime-box.css` framing, and `BrutalistPageStyle.astro` wrapper paint. The accepted website design now assigns one visual surface to the demo canvas. Toolbar and source are siblings outside that surface; demonstrated controls keep their own necessary borders.

## Ownership and implementation

`runtime-preview-surface.ts` composes the existing experimental `SitePreviewSurface` around the original `DemoSpec.root` through its ordinary anonymous slot. It adds no Base API, event, role, tab stop, named slot, or raw host target. The Prototype owns border, radius, fill, foreground and shadow. Normalized `surfaceStyle` supplies only width, padding, minimum height, flex arrangement and the existing closed theme input. Original demo refs, setup, uncontrolled state and cleanup stay with the demonstrated recipe.

Fixed-family previewers retain the accepted family and existing projection generation controller. Their explicit content closure adds only `site-preview-surface` to the original manifest's Prototype identities and retains the original component root identity. Generic/Base/custom demo and direct `prototypeId` previewers use the same existing `renderDemo` runtime renderer with the wrapped recipe. This does not turn the legacy generic switch into a page-wide atomic transaction. Color-mode updates change the closed theme values; a generic family update changes only the passive surface and keeps the example's state and identity.

`previewer-bootstrap.ts` owns lazy IntersectionObservers and pending client imports. It reads the current preference when activation reaches the client, revokes work on removal or Astro swap, and avoids duplicate initialization. A late import cannot initialize an old root even while that old root is still connected during a swap. The existing previewer remains the owner of runtime disposal. Loading, initial error and no-script fallbacks are readable, unframed native text.

Overview articles keep their headings, descriptions and destinations with layout only. The WC-only overview restriction is removed; lazy cards read the current public runtime preference. `DemoPreviewer` is the existing alias. `DemoMatrix` retains its explicit per-column runtime and supplies its canvas density through layout variables. `BrutalistPageStyle` remains a theme boundary. Homepage gallery surfaces, Copy integration, source highlighting, source expansion and install-manager controls are outside this change.

The existing `SitePreviewSurface` radius correction from unsupported `rounded-2xl` to supported `rounded-xl` is a separately owned integration dependency. The RuntimeBox change reuses it and does not extend that Prototype's inputs. Shadcn radius follows `--pui-radius-xl`; Brutalist uses zero radius. Browser assertions resolve the independent theme length instead of assuming an unrelated fixed pixel radius.

## Entry inventory and remaining boundaries

The source baseline contains 163 literal `PrototypePreviewer` call sites, two `DemoPreviewer` aliases, two `DemoMatrix` uses, and 34 Brutalist theme wrappers. Dynamic overview and matrix loops expand those call sites at render time. Normal fixed-family pages, toolbar-free/code-free examples, generic Base/custom recipes, direct-prototype API, lazy overview, and matrix all reach the shared canvas wrapper. The two homepage `HomeDemoPreviewer` uses have their separate existing gallery owner and are unchanged.

There are no separate components named `RuntimeBox`, `OverviewPreviewer` or `PreviewShell` in this baseline. Their production equivalents are the components and clients listed above. Generic legacy toolbar commands still retain their previous implementation; this surface change is not a claim that every website control has migrated. Code-panel and installation Copy changes remain a separate reviewed slice. The source panel can retain its own code-surface presentation because it is a separate source view, not a second ancestor frame around the demo.

## Evidence boundary

Executed local tests use real Web Component, React, Vue 3 and Vue 2 adapters with installed framework packages. The test loader replaces only the browser CDN imports; it does not prove the website's live network path. They cover slot/native node and focus identity, original setup/dispose, uncontrolled Toggle state and subsequent activation across a surface family change, exact recipe closure, reserved-ref rejection, late lazy import cancellation and duplicate initialization. An executed CSS fixture fails against the original overview article border and passes after removal. It is structural/source evidence rather than a browser pixel result.

The browser suite is registered in the explicit runtime test plan and the focused visual workflow. It covers the two families and four website runtimes, light-to-dark computed-paint deltas, 390px reflow, toolbar and demonstrated Select popups, generic Base commands, a below-fold lazy card using a changed preference, and no-script titles/links. The same paint predicate has mutation fixtures for duplicate frames, unsupported radius token, missing computed radius/border/shadow/fill, bad padding, semantic takeover, disabled subtree hit testing and overflow. A browser negative control reinstates the old ancestor border and must fail that predicate before restoring it.

Actual browser execution and screenshot inspection remain pending the exact integrated hosted Actions run. Captures write to the existing `homepage-evidence/runtime-box` artifact tree with source SHA, dirty state, viewport, family, runtime and measured paint. Local type checks, generated-CSS inspection and HappyDOM cannot establish visual acceptance.
