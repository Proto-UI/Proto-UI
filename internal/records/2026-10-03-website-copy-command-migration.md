# Website Copy command migration: first consumer slice

This record is an implementation/evidence note for #561 and #785. It adds no Base protocol, lifecycle admission, package publication, or all-site atomicity claim. The implementation baseline is local `71186ae77ed7532b87c01c46c543af162903fb92` (the tree published as `df16df4190447b9daa3581d7756ad26e46d53024`).

## Ownership and coverage

The migrated actions are ordinary Markdown/MDX ExpressiveCode Copy, `PrototypePreviewer/CodePanel` Copy (including CodeExample consumers), and `InstallCommandCard` Copy. One explicit `website-copy-command` consumer recipe uses the selected actual Shadcn/Brutalist Button, Lucide icon, and Base Live Region. Button owns activation, disabled/focus/press behavior and all command paint. The label remains authored content; success/error is a separate polite, atomic announcement. No imperative `aria-label` competes with Adapter projection.

The application Clipboard controller owns the immutable request payload, source revision, one pending operation, feedback timer, and disposal lifetime. Views are replaceable subscribers. Duplicate activation during a pending write cannot start a second write. Repeating after settlement replaces the feedback deadline. A source change invalidates stale success/error. An already submitted OS write cannot be cancelled; disposal prevents a late rejection from running the legacy fallback or touching the former page. The inherited EC legacy fallback remains explicit, checks `execCommand`'s result, and restores current focus/selection only while its temporary field still owns them.

Each Copy scope reuses the existing projection controller/materializer, lazy public runtime loader, explicit recipe closure and closed theme surface. Ordinary fences/install commands/independent CodePanels follow the page runtime preference. An embedded Previewer CodePanel follows that Previewer's committed runtime, not an uncommitted preference. Family follows the closest committed projection or site family. Failed preparation retains the prior truthful runtime; it does not relabel an old WC view as React. Initial failure leaves selectable source. A newer focus event wins over generation focus restoration. Clipboard completion does not request focus. There is no claim that all independent Copy scopes switch atomically with the homepage or other previewers.

## ExpressiveCode and #630 compatibility

### Initial retry and pending focus repair

Independent review found `R-COPY-INIT-RETRY-001`: after the first renderer failed, the controller had no committed generation and no start lease; a later selection called `request()` before restarting it. The Copy consumer now starts a fresh controller attempt from the latest selection only in that uncommitted idle state. Each attempt has a distinct projection owner namespace, so a late old loader/disposal cannot collide with the new attempt's generation numbering. The logical Clipboard owner survives. A failed change after a successful mount retains the existing controller and view. Tests discriminate the old React-only materialization from the required React → WC recovery, same-selection retries, and a slow restart superseded by a failed newer selection followed by a usable new attempt; they await actual late-host disposal before asserting the retained view.

Copy also stays enabled and focused during a pending platform write. The application owner already reserves one operation synchronously, so repeated native activations cannot cause overlapping Clipboard writes. Pending is conveyed by the real Lucide `loader-circle`, title and LiveRegion. This consumer policy avoids invoking Base Focus's intentional `setDisabled(true) → blur()` behavior; it does not change that contract. A real WC regression test observes retained focus, changed glyph/announcement and exactly one write under repeated clicks. Browser source checks both Enter and Space, verifies their focused target and retained focus, and checks Space does not scroll the page. These browser assertions still await Actions.

The EC frames option disables its inherited Copy markup, script and observer. The website plugin runs after frames preprocessing and retains filename handling, the processed exact code, and terminal full-line comment removal plus trimming. Payload is carried directly as an escaped HAST attribute; syntax-highlighted text and visual line wrappers are never the source. EC's independent overflow/focus behavior and the shared Shiki/EC palette remain in place.

The supplied displaced-glyph case was traced to EC's absolutely positioned `button::after` combined with the old zero-margin override. That Copy button and override are removed. Its replacement uses the actual Lucide child centered by the actual Button recipe. This is source evidence; final pixels await Actions.

The #630 Shadcn Copy target/glyph geometry stays 32px/18px. Radius and focus now come from Shadcn Button's `rounded-lg`/`ring-3`, replacing the former 6px/native outline CSS imitation. Brutalist uses its own 40px icon Button, square corners, hard shadow and ring-offset recipe. The updated #630 suite retains palette, overflow, selection, navigation and narrow viewport expectations while asserting the real command tokens, geometry, glyph center and focus paint delta.

Local checks use Node 24 and installed dependencies only. Focused tests cover real WC composition, native/outward event deduplication, complete props, family remount while pending, failed runtime retention, stale source/completion, repeated copy, late rejection/disposal, selection/focus preservation, page cleanup/reinitializing, EC terminal payload rules, and existing CodePanel/CodeExample behavior. No local browser/server was launched. The new Actions suite is explicitly listed in the runtime plan and homepage visual workflow. It exercises the actual browser Clipboard, injected platform failures/retries, no-JS source access, all four public runtimes and both families; it captures exact SHA, viewport, family/theme, geometry and before/after paint plus screenshots under `RUNNER_TEMP/homepage-evidence/copy-commands`. CodePanel expansion, package-manager selection and CodeExample host/file controls remain their existing owners. Full code-surface toolbar/frame/traffic-light unification and RuntimeBox surface work remain separate approved work. The #563 matrix is absent from this baseline; its source-bound Copy, expansion, EC focus and install rows, runtime evidence and reviewed lazy-adapter closure must be reconciled against the final integrated tree before that PR can claim compatibility.
