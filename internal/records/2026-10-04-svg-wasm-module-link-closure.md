## Independent-review binding repair

The first frozen candidate received a local `REQUEST_CHANGES`: destructured business bindings were mistaken for native WebAssembly globals. Six business shadow variants reproduced through both public validators, while genuine global controls stayed rejected. Renamed namespace/method extraction also exposed three related missed native entries per validator. The repair's initial additional reproduction therefore had 18 intended failures and six passing controls across 24 Website/Harness cases. The previously passing same-name extraction from `globalThis` was retained as a mandatory positive; merely registering an opaque shadow would have hidden it.

The new WebAssembly branch now separates complete lexical bound-name registration from possible native value projection. Scope includes parameters, nested object/array patterns, renamed names, defaults/rest, catch, block/loop lifetimes, function-scoped var, TDZ/hoisting and named expression bindings. Known browser global and WebAssembly values can be projected through static destructuring paths and local literal aggregates. Unknown business parameters stay unknown business inputs, not browser globals. Possible native default/rest values remain unverified; known rest exclusions and definitely present safe/business fields suppress unused native defaults. The existing DOM/ownership helpers were not changed or represented as upgraded.

All initial three-finding fixtures and the real MDX-remasking regression remain. Additional controls distinguish native defaults from unused defaults, known excluded rest properties from retained native methods, safe Memory/Table/validate extraction, numeric array-rest positions and shadowed versus native Reflect.apply receivers. No JavaScript or WebAssembly payload was evaluated. The first binding implementation hit a missing local property-name helper, corrected before broader checks; a subsequent array-rest control exposed numeric indexing being treated as an opaque property, repaired locally without changing the shared member helper. Both unsuccessful outputs are retained rather than relabeled as original causal reproductions.

Additional scope controls found and repaired two same-branch issues before renewed acceptance: an unknown global member call must not itself be labeled a WebAssembly entry, and var declarations in class static blocks or TypeScript namespaces must not hide a later outer browser global. The former reproduced six negative-control failures with four native-unknown positives; the latter reproduced four missed-global failures with four inner-business controls. Runtime enum/namespace/import-alias names also suppress global identity, whereas type-only names do not. These refinements remain local to the new WebAssembly environment; they do not modify the shared DOM helpers.

Binding-pattern and class-static-block scope expectations follow ECMAScript's [BoundNames](https://tc39.es/ecma262/multipage/syntax-directed-operations.html#sec-static-semantics-boundnames) and [static initialization block](https://tc39.es/ecma262/multipage/ecmascript-language-functions-and-classes.html) rules. Source fixtures inspect syntax and diagnostics rather than executing these example bodies.

## Independent-review TypeScript erasure repair

The second local review resolved the prior shadow finding but found erased TypeScript declarations impersonating runtime shadows. A new 20-case Website/Harness reproduction had twelve intended misses and eight passing controls: ambient const/qualified declarations, ambient and pure-type namespaces, import-type and inline type imports suppressed a real remaining native call. True business/value declarations, a type-alias control and the qualified native control stayed distinct.

The correction is local to the WebAssembly binding predicate. Explicit type imports, ambient declaration ancestry and bodyless function signatures do not establish emitted shadows. The existing locked TypeScript namespace-instance classifier distinguishes `NonInstantiated`, `Instantiated` and `ConstEnumOnly` rather than reimplementing namespace emission from member names. For example, a namespace containing an `export declare const` still emits an empty namespace shell, so it is not equivalent to a namespace containing only interfaces/types. Mixed imports and real value namespaces/classes retain their controls.

Const enums were not treated as ordinary type erasure. Static oracles using the locked compiler show ordinary const enum values under isolated emission and member-reference inlining under a virtual, no-library/no-resolution full-program emit. Ambient const enums and const-enum-only namespace shells depend on emit settings; they therefore cannot prove that a same-named browser value was replaced. Their possible native entries remain unverified, without asserting the emitted program definitely calls native WebAssembly. These oracles only produce and inspect JavaScript text. Generated code, source expressions, WASM bytes, configuration and network requests were never executed. No production emitted-byte gate, dependency, manifest or old DOM/ownership predicate was introduced or changed.
