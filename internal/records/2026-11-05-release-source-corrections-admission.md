# Release 0.3 source corrections: required-entry admission

## Context

The merged audit of PR #1286 reported F1 (P2) in the release-0.3 source reader. `loadEffectiveLedger` in `scripts/ci/release-source-ledger.mjs` validated every supplied correction entry, but did not require the recorded correction to be present. A companion with a valid frozen binding and `corrections: []` therefore loaded successfully and returned the historical snapshot: 1233 criteria and zero Issue #649 conditions, silently dropping the five restored obligations.

This record documents the source-only repair and the validation actually run on it. The repair branch was created from `ec9ea70b8e1f1e2ff356091daf99221a605ad8c8`.

## Observed facts (retained, pre-fix)

The parent-owned probe in `/tmp/release03-ledger-required-entry-before-20261105.json` and `.mjs` ran the unchanged reader at the base revision:

- The real companion loads 1238 criteria in total and 5 Issue #649 criteria.
- An otherwise valid companion header with identical raw source bytes and `corrections: []` was **not** rejected and returned 1233 criteria with 0 Issue #649 criteria.
- The assertion requiring that input to be rejected exited 1.

The failure was therefore observed against the actual reader, not inferred from a static reading.

## Decision

The reader now binds required correction membership to the frozen snapshot's actual byte identity:

- `requiredCorrectionsBySourceSha256` maps the frozen ledger sha256 `7b8d96ab6368dbb36764346932fd737d5e127c8b27aeb1208d0337b0a3c11a5e` to the correction IDs any companion bound to those bytes must retain.
- After the existing snapshot-binding guard, the reader collects the supplied correction keys and requires each registered ID with a subset check (`new Set(...).has(...)`), throwing `missing required source correction <id>` before the ledger can be returned.
- The check is keyed by the hash of the bytes actually read, not by a self-declared companion field.

The frozen snapshot and its companion were not edited.

## Rationale

- Subset membership closes the omission without fixing a denominator: there is no total-criteria assertion, entry-count comparison, or complete-companion hash in the admission path.
- A future separately valid additive correction may append a new entry; it is still judged by the existing per-entry binding, provenance, duplicate-key and completeness checks.
- `corrections: []` is not treated specially; an omitted, truncated, or renamed required entry fails the same membership requirement.

## Follow-up

If the recorded correction ID is renamed or its companion entry is replaced, update `requiredCorrectionsBySourceSha256` in the same governed change. Added corrections remain subject to the existing per-entry binding, duplicate, and completeness validation; no new total or companion-hash admission gate was introduced.
