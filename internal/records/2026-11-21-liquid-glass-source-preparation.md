## Engineering decisions

The previous round removed most repeated color conversion work but still performed two seven-tap CPU passes when a dynamic backdrop changed. The source lease also copied the complete fresh `getImageData` snapshot into another byte buffer. Both costs are independent of how many pixels the final small button displays.

The candidate keeps the existing `[1, 6, 15, 20, 15, 6, 1] / 64` filter and separate rounding after each axis. The CPU path packs independent channels into 16-bit lanes, whose bounded integer sums cannot carry into their neighbors. Its scratch storage is bounded to the current size and retired with the optical program. Each retained filtered result has independent storage; reusing an output buffer across distinct cached sources would corrupt the older entry. Exact-byte reference checks, not visual similarity, govern this change.

The integrated prepared-source cache retains the preceding commit's four-entry, 4 MiB filtered-RGBA budget, exact source identities, weak historical ownership, old-revision retirement and single-entry behavior without `WeakRef`. CPU and GPU prepared results share this budget. GPU entries own separate output textures and release them on eviction, invalidation or disposal; raw and horizontal-pass textures are reused within the helper. This is a retained-result budget, not a bound on all source, scratch, readback, browser or GPU memory.

For the source lease, native `getImageData` already creates an independent snapshot. A `Uint8Array` view now adopts that snapshot's exact `byteOffset` and `byteLength`, removing one full-backdrop allocation and copy per successful source draw. It does not borrow the live canvas backing store or reuse bytes across source revisions. Opacity validation, revision reentry checks, origin-clean reset/recovery and synchronous revocation remain in place.

A separate GPU prefilter candidate is being verified against the same original byte arithmetic. It must establish fragment, varying and sampler precision, preserve both RGBA8 rounding boundaries, isolate its temporary GL state, and release all owned textures/framebuffers. Independent review identified that `gl_FragCoord` alone does not inherit the fragment's declared high precision; the candidate instead uses a high-precision varying and canonical texel centers. The native matrix includes 2048-pixel axes as well as narrow and odd dimensions. This is a specification-based portability correction, not a reproduced device failure: [GLSL ES 1.00](https://registry.khronos.org/OpenGL/specs/es/2.0/GLSL_ES_Specification_1.00.pdf), sections 7.2 and 4.5.3, define the built-in input precision and default-precision scope respectively. The existing main optical shader and final readback/contrast/decode checks remain authoritative. Until actual WebGL byte comparisons and matched browser measurements succeed, this is a candidate, not an accepted GPU speed or visual-equivalence claim.

The independently reviewed scene-theme repair and its exact source binding are recorded in [the local-appearance record](./2026-11-21-liquid-preview-local-appearance.md). It resolves the scene's canvas/palette from the same scope its observer watches. The ordinary outer CSS theme projection remains separately owned; incompatible foreground styling still causes honest fallback.

Scope-override canvas pixels also pass, but an opposite-theme backdrop can remain incompatible with the independently owned outer heading color; this is not complete local-theme CSS or visual acceptance.

The complete run nevertheless fails. All four fixture adapters reach `opaque-fallback` with `gpu-prefilter-failed`, so optical readiness times out. The candidate records zero timed workload windows and zero attempted fresh presses; each mode retains all sixty planned presses as unattempted and latency remains null. Its six failures are four adapter smoke timeouts, one matched-workload readiness timeout and one initial fresh-press readiness timeout. The comparison correctly exits nonzero. There is no candidate performance measurement to compare with this run's valid baseline.

Investigation identifies a lifecycle hypothesis supported by [OpenGL ES 2.0 section 2.10.3](https://registry.khronos.org/OpenGL/specs/es/2.0/es_full_spec_2.0.pdf): deleting a current program defers actual retirement until it is unbound. The old `clear()` could leave that object current while a new helper captured/restored state. Switching away and then restoring the retired object could generate the later strict GL failure. The minimal repair unbinds the program with `gl?.useProgram(null)` before deleting owned resources. It does not consume errors or relax any rejection. A delete-pending state-model regression first fails on the old source with `gpu-prefilter-failed`, then the repaired program/helper suites pass 112/112, independently repeated; scoped types also pass. Actual old/new program traces remain the next native check, so the state-model result is not presented as completed native root-cause proof.

The repaired program SHA-256 is `25706f5254d6f6d6c31413d53baf7b46aafdd15c463648ccdf48ce0031ffa5b2`. The helper remains `88532e51a79b27178f8949fd3542b2c33e6d55dd0cce445d5b261ce0a3d4f09f`. The CPU `prefilter` function is byte-identical to the measured `19d175f` version, with function SHA-256 `730021abb83471a19ddb88378174dd29eba054b25f3574aadfc5dd802b51c5ca`; its reports keep their original candidate binding.

## Remaining acceptance

The repaired candidate still needs actual old/new program lifecycle traces and a complete same-runner browser performance/visual rerun. The helper's successful byte matrix does not substitute for those failed integration criteria. The broader pre-existing prototype and compiler failures remain unresolved separately. Physical 120 Hz and input-to-photon acceptance require suitable real hardware. The existing draft PR also retains its independent platform review and responsible-author DCO requirements; no certification or approval is manufactured by this record.

Apple's [Materials HIG](https://developer.apple.com/design/human-interface-guidelines/materials) and [rendering-efficiency guidance](https://developer.apple.com/documentation/xcode/improving-your-app-s-rendering-efficiency), retrieved 2026-11-21, support readable Regular material, restrained emphasis, stopping completed animation and avoiding unnecessary background work. The implementation and numerical optimization here are independently authored Web engineering decisions, not Apple's private material implementation or timing requirements.
