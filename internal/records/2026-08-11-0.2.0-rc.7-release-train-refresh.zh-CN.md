## 旧 draft 分支的处理方式

旧 #355 的三个准备提交不应直接叠加到当前 `main`：

- 39-package BOM、Brutalist 非 launch commitment 与 CLI `add` 延后已经过时；
- Brutalist README/manifest、metadata sync、launch policy、surface map 与 V entity 已在后续 PR 中获得更完整的 source-of-truth 更新；
- 当前 BOM 应继续由 `pnpm release:bom` 生成，不能用旧分支版本手工覆盖；
- 旧准备记录中 39-package publication runbook 不再适用于当前 40-package workspace set。

因此 release PR 应从当前 `origin/main` 重建最小差异，只保留当前双语 release notes、V entity refresh 与本记录，而不是机械解决旧分支冲突或恢复旧投影。

## 验证与发布边界

全部 40 个公开 identity 就绪后，完整 `release:rehearse` 可通过公开 registry-readiness 并继续执行 source、catalog、type、test、build、stage、dry-run、consumer 与 docs 检查；但该公开门禁通过不构成私有 Trusted Publisher 配置证据。不得绕过发布门禁，也不得复用旧分支的临时 snapshot digest 或验证计数作为最终发行证据。

准备 PR 合入后，真实 publication 必须从合入后的 `main` 手动运行 `release-packages.yml`，使用 `mode=publish-all`、`profile=workspace` 与正常路径下的 `resume_published=false`。只有全部 40 个 package 发布成功后，workflow 才可推进 npm `next`、创建 `v0.2.0-rc.7`、GitHub prerelease 与不可变 spec snapshot。随后再从最新 `main` 建立独立 evidence PR，核对 registry、dist-tag、tag、release assets 与 digest，并把 V entity 从 `draft` 激活。
