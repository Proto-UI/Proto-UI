# 序章：我们还要发明多少遍 Button？

毫不夸张地说，一直以来，我们在 UI 交互组件的基础建设上做了大量的重复工作。

- 每一个对 UI 有设计调性要求的公司，或多或少都会定制自己的组件库。在这个过程中，Button、Switch、Select 等组件的基础行为也会被一遍遍重新实现。
- 当公司规模稍大，或者产品存在不同的运行环境时，同一个产品内部使用多种技术栈、同时要求它们保持一致，也是一种很常见的需求。

这些工作并不只是把同一种颜色和圆角重新写几遍。

让我们看一个很普通的 Switch。无论它最终被写成浏览器中的 DOM 与脚本、某个框架里的函数、移动端的 widget，还是桌面 UI 工具包里的控件，它通常都要处理一批似曾相识的问题：保存当前是 on 还是 off，接受点击、触摸或键盘输入，把状态反馈给用户，处理焦点和禁用状态，让辅助技术能够理解它，以及在状态变化后把结果报告给使用它的软件。

具体代码当然不能直接复制。不同技术的结构、状态方案、事件系统和渲染方式可能相去甚远。真正有些奇怪的是：实现一次次变得面目全非，这些交互责任却一次次回到我们的待办列表里。

如果项目处在一个足够成熟的单一技术生态中，这些工作通常能由现成的组件库，特别是 Headless 组件库缓解。比如说，Radix 在 React 生态中积累了许多经过实践检验的交互和无障碍处理。它至少说明了一件很重要的事：组件里确实存在一些值得从单个产品中抽出来、由更多人共同维护的知识。

只是，这种复用通常有很清楚的技术边界。一旦我们开始追求多个技术选型之间的一致，合适的基础就没那么好找了。然后我们可能会苦恼于：

- 我想获得 Radix UI 那样的无障碍交互支持，但项目不一定能使用 React；
- 我想采用 shadcn/ui 的视觉风格，但当前技术栈没有足够成熟的社区实现；
- 公司已经维护了一套 React 组件库，但由于新的业务需要，现在还得继续实现 Vue、Web Components、移动端或桌面端的版本。

这不是现有组件库做得不够好。它们本来就在解决各自生态里的问题。只是当交互知识和某种具体实现绑在一起时，它就很难自然惠及其他技术；等到团队更换框架或平台，许多已经解决过的问题仍然可能需要重新解决。

因此，长期维持多种实现之间的设计风格、交互细节和无障碍质量，通常需要持续而昂贵的专门投入。保持这些一致性，一直都“不便宜”。

可这些工作真的必须随着每一次技术更替，从头再做一遍吗？

反复出现的责任，并不能直接证明它们一定能够形成跨技术的公共抽象。不同平台之间的差异，也可能只是把原先分散在各个实现里的复杂度，转移到一个新的中间层。增加一层抽象，也不会自动带来一致性或可靠的无障碍支持。

但至少，这些重复值得我们检验一个更有限的猜想：在人机交互中，是否存在一些不必随实现技术一起重写的稳定逻辑？我们能否把它们找出来、清楚地记录，再放进不同技术中检验它们是否仍然成立？

如果这个猜想成立，那么一部分交互知识就有机会成为可以长期积累和共享的公共资产，而不再被某个框架、平台或技术生命周期独占。如果它在某些组件、媒介或平台上不成立，那些失败也会帮助我们看清这条边界究竟在哪里。

这就是 Proto UI 想要探索的可能性。

不过，在讨论如何保存这些交互知识之前，我们还需要回答一个更基础的问题：如果代码、节点、控件乃至整棵渲染树都不是那个稳定的对象，那么当我们指着不同实现说“它们是同一种组件”时，我们认出的究竟是什么？
