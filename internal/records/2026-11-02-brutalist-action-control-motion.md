## Source findings and decision

Button's draft P-BRUTALIST-BUTTON-MOTION already specifies transition-all,150ms,cubic-bezier(0.4,0,0.2,1), reduce/unknown static. Raised Surface and elevated Select had matching motion endpoints but no timing rules. Add only that missing preference policy. Keep rules inside each owning setup for source lowering; do not duplicate a Base behavior hook or add site-local CSS.

Flat geometry does not imply a prohibition on color transitions. Current flat Trigger rest/hover/press all use bg-main/text-main-foreground/border-black, so no differing color endpoint exists to interpolate. Header recipe explicitly opts into elevated; the authored Brutalist Select demo omits appearance and remains flat. Generic controls without the Header opt-in also retain defaults. These are source identities, not verified deployment identities. This first slice does not settle the user's whole Select request.

Community icon recipes use secondary/default/all/raised Surface, while action helpers also consume that public Surface. Native anchors keep their semantics. Only raised non-fading Surface gets timing; fade retains its opacity clock. Switching elevation/appearance/fade withdraws the new rules. No default-category transition-none override is added.

Retain transition-all because the current Button criterion names it and there is no existing transform/translate/box-shadow-only combined token in the fixed CLI. Do not concatenate two competing transition-property tokens, drop shadow motion, or quietly change compiler vocabulary. This choice is provisional pending actual theme/resize/focus contrast and geometry controls: animating all can affect more than hover, and static equivalence is not acceptance.
