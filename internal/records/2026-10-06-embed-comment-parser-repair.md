# Preserve quoted comment markers during embed scanning

Date: 2026-10-06. Baseline: PR #563 `f5a0a226cd4407229332d7d7c3bb20b6109197c7`.

The existing Website/Harness native-embed policy already rejects unreviewed iframe/object/embed/webview surfaces. Its global HTML-comment regex nevertheless removed a real iframe between two quoted attribute values containing `<!--` and `-->`. Browser parsing treats those marker bytes as attribute data, so this is a defect within the declared profile rather than a request to model another runtime API.

The baseline fails three Website HTML/Astro and Harness HTML probes while nine paired controls pass. The repair uses the already-locked parse-only HTML/Astro parsers to identify actual comment nodes. Only parser-proven ranges are masked, using whitespace and preserved line breaks. parse5 positions already use JavaScript code units; Astro reports UTF-8 byte positions, which are converted to requested code-unit boundaries in one source pass. It never concatenates bytes across a removed comment. Parser uncertainty leaves the original bytes for the existing fallback; comment-looking quoted data is never erased speculatively. Existing script selection and the exact style-isolation embed boundary are unchanged.

Forty-five end-to-end focused cases and fifty exact production-helper range assertions pass, including quoted markers around an actual embed, real comment controls, script-string examples, non-BMP characters before comments and immediately following active embeds, no synthesized tag joining and comments followed by active embeds. Independent review found that the first candidate incorrectly assumed Astro offsets were code units: non-ASCII inside a comment could erase the start of the next iframe. That unpublished candidate was repaired with explicit byte-to-code-unit conversion and direct whole-output/suffix assertions across ASCII, BMP, non-BMP, combining text and CRLF. The earlier emoji-prefix controls alone had not established masking correctness.

Full coverage/source validation and independent read-only acceptance remain separate final-tree steps before publication.

The same review also requested Range#createContextualFragment and CSS Modules/ICSS composition profiles. These are not declared implemented forms, and a 2026-10-06 apps/www/packages search at the baseline (excluding node*modules/dist) found no such usage or *.module.\_ sources. That is a time-bound observation, not a safety guarantee or exemption. The maintainer's finite-scope direction keeps these as explicit future profile work in #854, with independent acceptance criteria; they are not represented as repaired functionality or allowed promotion evidence here. No generic JavaScript interpreter, new dependency-language admission or blanket allowlist was added.

The baseline's main CI, all applicable dedicated evidence workflows and DCO passed before this increment; one conditionally inapplicable workflow was skipped, while Vercel's separate build-rate-limit state remained unresolved. Those completed results are baseline evidence, not a claim that the new candidate's remote CI has run. Existing human review remains an integration requirement.
