## Compatible neutral-paint continuation

A source notification still cancels its pending image request and synchronously runs source, style, geometry, preference and ownership admission. The optical program's original pure input checks are shared with this path: tint envelope, output bounds, source dimensions and byte length, the complete per-call source-alpha scan, and finite contact values. These checks run before the source signature shortcut. The program repeats them for every real render, before initialization or preparation. Pure admission does not prove GPU success or final pixel contrast.

Only a binding that already owns an actually decoded neutral image for the same paint lease, and is completely at rest, may continue its expensive source rendering in a browser task. A claimed but not decoded SSR image, active pointer contact, keyboard press, release animation and cancelled contact are excluded. The continuation reads the latest state and re-enters the complete rendering and image-preparation path; it does not capture a source frame or produce an unvalidated placeholder.

Each binding owns one cancellable latest-state task. Compatible source notifications keep the existing queue position rather than postponing it repeatedly. The native scheduling API is feature-detected and uses `user-visible` priority with an owned abort controller; the portable zero-delay timer fallback has no priority or deadline guarantee. Fresh input, non-source repaint, fallback, replacement, context loss, adoption and disposal cancel the task. The existing fresh-down microtask and pointermove RAF behavior remain in place.

Internal document observations count logical tasks scheduled, run and cancelled, plus pending tasks. They do not count backend transports as separate work or claim a scheduling SLA. Retirement clears captured closures before invoking cancellation callbacks, and callback ownership prevents a retired task from erasing a reentrant successor. Captured backend capabilities and post-construction ownership checks prevent a capability getter or constructor from submitting a task after synchronous disposal.

## Recovery of deleted current-program state

The owning program's `clear()` deleted the current WebGL program without first unbinding it. A subsequent prefilter state snapshot could retain that marked-for-deletion object; restoring it with `useProgram` generates `INVALID_OPERATION`, which the existing error check correctly rejects. This is consistent with the failed native observations, although that artifact contains no per-call GL trace proving its first error.

A controlled regression models the WebGL marked-object rule and reproduces `render → clear → render` failing with `gpu-prefilter-failed`. An independent probe executes the actual production program and helper against a separate GL lifecycle model: repeated render succeeds, clear/rebuild fails, and explicitly unbinding before the rebuild repairs the control. The production correction calls `useProgram(null)` before deleting owned resources. Both controlled reproductions then pass. Error consumption, GPU rejection, contrast checks and the optical shader remain unchanged. The next native run adds a real-program clear/rebuild and multi-source comparison outside latency timing, alongside the original 84-case helper matrix.
