# Independent review: Date Picker selection completion ordering

Reviewer: `/root/collections`; read-only definition/source review. The implementation owner is `/root`. This file records the definition review before the repair and the subsequent bounded implementation review. The three reviewed working-tree files are bound by `collections-agent-datepicker-review-source.json`.

## Confirmed original regression

The four existing Date Picker cases in `packages/prototypes/base/test/selection-reset-lifecycle.test.ts` expect normal `valueChange` followed by `openChange`, and only `valueChange` when its synchronous callback unmounts, disposes or remounts the Root/Day. The original `dc3b184ba10b0de53e40359c52d012b204b2cd01` baseline reproduces all four failures; the shared-input owner retained `intake/datepicker-dc3b184-baseline-red.log`. The original assertions were not weakened.

Independent source inspection identifies the order: Calendar `requestSelection` updates canonical state and calls `publish`; `publish` immediately creates `selectionCommit` for an accepted value; Date Picker's context subscriber requests Popover closure; Calendar emits the outward change event only afterward. Completion therefore races ahead of the application callback that is supposed to be able to retire that continuation. None of the collection slice's implementation changes touched these source files.

## Definition review

`C-CALENDAR-SELECTION-0001` already assigns canonical selection and accepted completion to Calendar, retains compatible single-date callbacks, permits synchronous and delayed controlled acceptance, retires pending completion on superseding selection/owner replacement/unmount/disposal, and forbids stale requests from closing a reentered popup. Its Picker criterion permits closing only for a live canonically accepted complete request. The general monotonic view-operation definition likewise forbids revival after withdrawal. The observed close-before-change ordering is incompatible with the existing retained lifetime boundary; a new public API or wider semantic rewrite is unnecessary.

A narrow clarification to the Picker criterion is appropriate: accepted completion can be delivered only after the corresponding outward value/range change callback has returned, while the originating owner/view/request remains current. Synchronous controlled acceptance inside that callback may update canonical day facts, but it must not deliver the close continuation ahead of the callback's lifetime decisions. This clarification keeps the definition draft and does not claim stable browser/AT admission.

Canonical state and the request ID may still be published before the outward callback. That early publication is needed to capture whether the popup was open when the request began. Moving the entire publication afterward would incorrectly treat a popup first opened inside the callback as belonging to the old request. The implementation should separate request/canonical publication from eligibility to publish accepted completion.

## Repaired implementation and retained controls

The implemented `pendingSelection.proposalDelivered` separates canonical/request publication from accepted completion. The first publication continues to capture the request's original open session and can update day facts. Matching canonical acceptance cannot create a new `selectionCommit` until the proposal delivery returns. The continuation then verifies the captured owner, view epoch and selection ID, requires the same current pending request, enables completion and republishes the current canonical facts. A retired view, unrelated owner replacement or valid superseding request cannot revive the old continuation. No exception handler, raw DOM repair or forced reopen was introduced.
