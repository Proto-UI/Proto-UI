# Website self-hosting coverage matrix

This document is the non-normative M0 operational ledger for issue #420. It inventories the website surfaces that must either consume Proto UI through the approved website boundary or carry an explicit native/infrastructure disposition. `spec/**` remains authoritative; this ledger does not promote an entity or create a semantic guarantee.

Snapshot basis: repository commit `3b29193950327ed0ee24d86b61f10d9dedf016aa`, plus a source scan of `apps/www/src/**`, `apps/www/astro.config.mjs`, and `apps/www/package.json`. Runtime, screenshot, and multi-frame evidence are deliberately called out as missing in the baseline ledger below rather than inferred from source.

## Lifecycle stop condition

The #420 comment policy requires website consumers to use merged, stable Proto UI surfaces and never consume draft entities. On this snapshot, every relevant Base, Shadcn, and Brutalist `P-*` prototype entity is still `draft`. Merged implementation and passing implementation tests are evidence of current behavior, not lifecycle promotion. The contradiction is unresolved and this matrix does not silently choose a side: rows that need those prototypes remain `blocked` or `research` until the applicable entity chain is stable and the website consumer evidence exists.

The adapter foundation is narrower than the prototype inventory. `D-ADAPTER-PROFILE-0001`, `A-WEB-COMPONENT-0001`, `A-REACT-18-19-0001`, `A-VUE-3-0001`, `A-VUE-2-0001`, and `T-ADAPTER-PROFILE-0001` are `active`. Specialized A11y, Collection, Scroll, Text Control, and Positioning support/capability slices are not cataloged in those profiles, so this ledger must not treat their absence as support.

For the website only, the primary Proto UI production host is the generated Web Component facade. React and Vue runtimes may appear in reviewed raw-adapter demonstrations, but must not enter the documentation shell or ordinary website controls. This website choice is not a cross-project host policy.

## Reading the matrix

- `official-prototype` is a direct generated-facade consumer once the prototype and its evidence are stable.
- `site-composition` combines approved Proto UI primitives while the website retains only application state and content policy.
- `native/static` intentionally uses semantic HTML with no Proto UI-owned interaction state.
- `infrastructure-exempt` is build, routing, indexing, or demonstration infrastructure that is outside the ordinary control consumer wall. Every such row has a reason and a re-review trigger.
- Difficulty uses `F1` through `F5`, from mechanical inventory work to cross-domain interaction and equivalence work.
- Slice references such as `S9` point to the proposal index below. They are planning labels, not created Issues or semantic approval.

## Enforcement plan

The M0 checker and its normal CI wiring must enforce all of the following before this ledger can act as a durable gate:

1. Every relevant website override, local component, client script, interactive MDX component, and inherited Starlight interactive slot maps to exactly one row or an explicitly declared grouped row.
2. Row IDs are unique, stable, lower-case `www.<area>.<surface>` identifiers; headers, target classes, states, strategy labels, and state totals use the exact machine contract.
3. Inventory drift fails on unmapped components/scripts and on matrix rows whose declared evidence paths no longer exist. Renames require an explicit ID migration decision rather than silent ID churn.
4. Every `blocked` or `research` row links an Issue and names its owner. Every native or infrastructure disposition states its reason, owner, and concrete re-review trigger.
5. Every raw consumer-wall escape links a removal/formalization Issue. Raw prototype, adapter, runtime, or theme imports are limited to a reviewed demonstration/integration allowlist.
6. The generated Web Component facade is asserted as the primary website control host. Production bundle checks reject accidental React or Vue runtimes in the shell while permitting isolated, lazy demonstration chunks.
7. Static analysis rejects new app-owned keyboard, focus, scroll, dismissal, selection, or ARIA state machines in ordinary website controls unless an explicit reviewed matrix disposition covers the exact path.
8. WC SSR/light-DOM fixtures exercise pre-upgrade, post-upgrade, no-JS, repeated mount, remount, and dispose behavior. Adapter-specific raw demos remain separate from ordinary website consumer proof.
9. Normal CI runs the checker, import-boundary checks, production build, bundle assertions, focused browser fixtures, and negative fixtures that prove each rule fails for a deliberate violation.
10. Closeout review reconciles every row against retained build, accessibility, screenshot, and multi-frame evidence. It changes state only when both lifecycle authority and executable consumer evidence support the change.

## Residual decisions that this ledger does not make

- It does not promote draft Base, Shadcn, or Brutalist prototypes merely because implementations or tests exist.
- It does not infer specialized A11y, Collection, Scroll, Text Control, or Positioning support from the active general adapter profiles.
- It does not decide the final WikiTerm, table-of-contents, mobile-navigation, search, or selection semantics; their dependency rows keep those decisions visible.
- It does not turn the website-specific generated-WC host policy into a policy for other applications.
- It does not treat demonstration-only raw adapter access as permission for implementation-internal imports elsewhere on the site.
