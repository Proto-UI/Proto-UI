## Lifecycle stop condition

The #420 comment policy requires website consumers to use merged, stable Proto UI surfaces and never consume draft entities. On this snapshot, every relevant Base, Shadcn, and Brutalist `P-*` prototype entity is still `draft`. Merged implementation and passing implementation tests are evidence of current behavior, not lifecycle promotion. The contradiction is unresolved and this matrix does not silently choose a side: rows that need those prototypes remain `blocked` or `research` until the applicable entity chain is stable and the website consumer evidence exists.

The adapter foundation is narrower than the prototype inventory. `D-ADAPTER-PROFILE-0001`, `A-WEB-COMPONENT-0001`, `A-REACT-18-19-0001`, `A-VUE-3-0001`, `A-VUE-2-0001`, and `T-ADAPTER-PROFILE-0001` are `active`. As of the 2026-10-06 pinned source audit, these profiles now catalog bounded A11y, Collection, Scroll, Text Control, Positioning and Table support/capability slices. Read each exact supports/provides relation and its evidence limit. Active profile identity does not activate a draft Module or Prototype, establish full compatibility, or certify non-Web and assistive-technology behavior.

The current website retains the user-approved sitewide Web Components, React, Vue 3 and Vue 2 preference. Homepage action groups and its gallery share a projection transaction; inventoried documentation commands, Typography and passive surfaces reuse the reviewed renderer with their own ownership and lifetimes. Static Astro content, native navigation, the theme service, Pagefind and retained WC-only bridges remain explicit boundaries. Framework Adapter acquisition stays lazy behind exact reviewed renderer/import pairs. This supersedes the old WC-only shell assumption, not the lifecycle stop condition: implemented consumers remain blocked or research until their applicable stable entity chain and consumer evidence exist. No state migration, cross-host equivalence, blanket shell exemption, or cross-project host policy is implied.

## Reading the matrix

- `official-prototype` is a direct generated-facade consumer once the prototype and its evidence are stable.
- `site-composition` combines approved Proto UI primitives while the website retains only application state and content policy.
- `native/static` intentionally uses semantic HTML with no Proto UI-owned interaction state.
- `infrastructure-exempt` is build, routing, indexing, or demonstration infrastructure that is outside the ordinary control consumer wall. Every such row has a reason and a re-review trigger.
- Difficulty uses `F1` through `F5`, from mechanical inventory work to cross-domain interaction and equivalence work.
- Slice references such as `S9` point to the proposal index below. They are planning labels, not created Issues or semantic approval.

## Enforcement plan

The M0 checker and its normal CI wiring must enforce all of the following before this ledger can act as a durable gate:

1. Every relevant website override, local component, client script, interactive MDX component, and inherited Starlight interactive slot maps to exactly one row or an explicitly declared grouped row.
2. Row IDs are unique, stable, lower-case `www.<area>.<surface>` identifiers; headers, target classes, states, strategy labels, and state totals use the exact machine contract.
3. Inventory drift fails on unmapped components/scripts and on matrix rows whose declared evidence paths no longer exist. Renames require an explicit ID migration decision rather than silent ID churn.
4. Every `blocked` or `research` row links an Issue and names its owner. Every native or infrastructure disposition states its reason, owner, and concrete re-review trigger.
5. Every raw consumer-wall escape links a removal/formalization Issue. Raw prototype, adapter, runtime, or theme imports are limited to a reviewed demonstration/integration allowlist.
6. Production bundle checks enforce the exact reviewed facade and shared-renderer owner pairs, permitted Base/Web Component closure and lazy React/Vue Adapter acquisition. The four-runtime preference can reach the inventoried Homepage, documentation command, Typography and passive-surface consumers; this is not a directory-wide or arbitrary shell import allowance. The media and native-link WC bridges remain explicitly inventoried. Every raw source/import pair and runtime entry requires review; lifecycle and surrounding semantic owners are unchanged. Active-document SVG admission remains unresolved and the bounded static image serializer is not a general sanitizer.
7. Static analysis rejects new app-owned keyboard, focus, scroll, dismissal, selection, or ARIA state machines in ordinary website controls unless an explicit reviewed matrix disposition covers the exact path.
8. WC SSR/light-DOM fixtures exercise pre-upgrade, post-upgrade, no-JS, repeated mount, remount, and dispose behavior. The other selected runtime consumers require their own composition, fallback and lifecycle evidence; raw adapter demos do not substitute for ordinary website consumer proof.
9. Normal CI runs the checker, import-boundary checks, production build, bundle assertions, focused browser fixtures, and negative fixtures that prove each rule fails for a deliberate violation.
10. Closeout review reconciles every row against retained build, accessibility, screenshot, and multi-frame evidence. It changes state only when both lifecycle authority and executable consumer evidence support the change.
11. Promotion remains a two-step workflow: implementation lands first; a later evidence/promotion change references that merged base commit (or an older allowed ancestor) and retains a machine-readable `Results:` manifest for the exact commit and tree. The manifest records executed commands and statuses plus every retained artifact path, byte size, and SHA-256 digest. Evidence captured only on an unmerged feature head is not ancestry proof after a squash merge and must be regenerated against the merged base before promotion. For pull requests, the full CI suite runs on GitHub's default synthetic merge checkout so the candidate is tested with its base. `COVERAGE_BASE_REVISION` and `COVERAGE_HEAD_REVISION` separately bind evidence to the exact pull-request base and head; `COVERAGE_MERGE_REVISION` identifies the temporary integration commit only so the checker can reject it as evidence. Never retain the merge SHA in an evidence `Commit:` or `Results:` manifest. CI fetches full history; local promotion validation must supply the same explicit base/head inputs.
12. Normal `check:coverage-matrices` is offline and validates `internal/coverage-matrices/github-governance-snapshot.json`. `check:coverage-governance-live` performs separate network reconciliation on Issue state events, daily, manually, and on pull requests changing the retained snapshot, matrices, checker, workflow or its declared dependencies. The PR lane uses the existing read-only token permissions and no repository secrets; changes to its workflow or checker still require independent source review. Maintainers explicitly edit sorted lowercase `owners` when matrix ownership changes, then run `coverage:governance:refresh`; the refresh updates only GitHub-projected facts and fails rather than guessing owner tokens.

13. Retained videos require the Linux real-decoder gate and explicit resource constraints in `scripts/coverage-matrices/README.md`. Decoder/toolchain absence is unverified, not signature acceptance. Different decoded frames are necessary media evidence, not sufficient interaction acceptance.

## Residual decisions that this ledger does not make

- It does not promote draft Base, Shadcn, or Brutalist prototypes merely because implementations or tests exist.
- It does not infer specialized A11y, Collection, Scroll, Text Control, or Positioning support from the active general adapter profiles.
- It does not decide the final WikiTerm, table-of-contents, mobile-navigation, search, or selection semantics; their dependency rows keep those decisions visible.
- It does not turn the website-specific four-runtime preference and exact consumer boundary into a policy for other applications.
- It does not treat reviewed demonstration/integration adapter access as permission for implementation-internal imports elsewhere on the site.
