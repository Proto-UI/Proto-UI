## 结论

Phase 0.1 已经形成一条可运行、可复验、可审计的 Agent 自主维护流水线。Agent 可以在一个有边界的 mission 中自主调查问题，经 fresh-context 独立核验后，在人类给出价值和语义决定的前提下完成修复、验证、独立复审和技术关闭。

它目前仍是人工触发、Skill 驱动的受控试点，而不是无人值守维护系统。单个阶段内的执行自主性已经较高，跨任务编排和预算调度仍然较低。更准确的描述是：

> 已实现“人工启动、Agent 高度自主执行、关键权限由人类治理”的技术闭环；尚未实现自动选题、自动创建 fresh task、自动回传结果和持续调度。

## 已形成的工作流资产

| 层次 | 资产 | 作用 |
| --- | --- | --- |
| 控制面 | 仓库级 `proto-ui-autonomous-maintenance` Skill | 根据当前记录选择下一个合法阶段，并维持权限边界 |
| 角色执行 | Observer、Verifier、Review Synthesizer prompts | 分离发现、事实核验和修复审查，避免同一上下文自证 |
| 人类门禁 | finding disposition、semantic decision、integration decision | 把事实、价值、语义和不可逆操作分开 |
| 审查材料 | finding 与 remediation-review templates | 记录行为变化、影响面、证据限制和残余风险 |
| 状态 | `mission-queue.yaml` 与 `runs.yaml` | 保存候选 mission、baseline、结论、人工决定和集成证据 |
| 确定性校验 | review-packet 与 run-ledger checkers | 校验路径、entity、anchor、baseline、状态迁移和 commit 证据 |

Skill 是工作流的控制面，但不是完整系统。完整执行面由 Skill、prompts、templates、fresh tasks、机器可读状态、确定性检查和人类权限门禁共同组成。

## 审查门禁实际产生的价值

独立审查不是形式性步骤：

- `AM-P0-002` 的第一版 remediation packet 过度扩展到 attachment rollback 和自动 capability recovery。审查暴露出无法稳定表达的生命周期状态，最终方案被收窄到 target preflight 和显式 retry。
- `AM-P0-003` 的第一轮 packet 被评为 `misleading`，因为遗漏第二处矛盾注释、混淆 Node 20 与 Node 22 证据，并模糊了语义 diff 和协调记录。修订后第二轮达到 `adequate`。
- 技术完成条件已经从“再找一个人泛化地批准代码”变成“独立审查 adequate、required validation passed、无 blocking residual risk”。语义和集成仍由人类决定。

## 成熟度判断

| 能力 | 当前判断 | 依据 | 主要缺口 |
| --- | --- | --- | --- |
| 有边界的自主调查 | 可用 | 3 个 mission 均产生可复验 finding | 尚未跑 no-finding control，不能证明不会制造工作 |
| 独立事实核验 | 较成熟 | 能纠正 finding 范围和 authority 表述 | fresh task 仍需人工创建和交接 |
| 限定范围修复 | 可用 | 已完成 test、runtime/spec、docs 三类变更 | 仍依赖人工语义授权 |
| 修复可审查性 | 较成熟 | 两次真实退回和修订证明门禁有效 | packet 质量仍受 Agent 表达能力影响 |
| 技术完成判定 | 已制度化 | checker 强制 adequate review 与 passed validation | 规则自动，跨任务执行仍手动 |
| 状态与证据治理 | 可用 | queue、ledger、commit evidence 可确定性检查 | 新 checks 尚未被 `.github` workflow 直接设为强制门禁 |
| 调度与预算控制 | 未实现 | Phase 0.1 明确为 manually triggered | 无 scheduler、controller、token budget policy |
| 结果自动回传 | 未实现 | fresh task 结果仍由维护者带回控制任务 | 缺少 task completion callback 和 handoff protocol runtime |
| 效率度量 | 证据不足 | 保存 elapsed、confidence、action value | token usage 和 human review minutes 多数为 `null`，样本量只有 3 |

## 当前不应作出的宣称

- 不能称为全自动项目维护系统。
- 不能由三次正向 finding 推断 Observer 具有稳定的 precision 或 recall。
- 不能把通过测试等同于影响面完整或产品语义正确。
- 不能因为技术完成自动化，就自动授权 commit、merge、publication 或 release。
- 不能把 operational records 当成 Proto UI 的第二套规范。

## 建议的下一组实验

1. 优先执行 `AM-P0-005` no-finding stop control，检验 Observer 能否在没有问题时停止。
2. 执行一个新的 discovery mission 后，用 `AM-P0-006` 做冻结基线 repeatability control。
3. 执行 `AM-P0-004` cross-Adapter lifecycle parity，扩大问题类型和可观察证据。
4. 用 `AM-P0-007` 测量剩余 verifies-anchor 完整性缺口，但不预设每个结构缺口都是运行时缺陷。
5. 开始可靠记录 token usage、人工决策时间、packet 修订轮次和 false mutation rate。
6. 只有在 no-finding、repeatability 和 attention saving 有足够证据后，再增加 thin controller 和 budget-aware scheduler。

## 总体评价

这次 PR 的主要成果不只是修复了三个问题，而是把一次性 Agent 对话抽成了一套可以重复执行、被独立质疑、被确定性检查、并在明确权限下进入代码库的维护协议。Phase 0.1 已足以继续做受控实验，但还不足以移除人工调度中心。
