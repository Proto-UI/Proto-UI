# Agent Operations

This directory defines the operational control plane for Agent-assisted GitHub work in Proto UI. It is not a project truth source and does not define Proto UI semantics. Applicable `spec/**` entities remain authoritative according to lifecycle.

Ordinary contributor Agents enter through `$pui-dev` and the composable skill registry in `skills.yaml`. Their capability and assessment rules live in `capability-policy.yaml` and `contributor-agents.md`. These files define task eligibility and routing; they do not grant GitHub permission.

A leaf may declare `allowedNextSkillIds` to constrain its nonterminal handoff to registered leaves sharing an entrypoint. The resolver returns this metadata and the handoff validator enforces it; `null` still permits an honest terminal result with the source leaf's required outputs. `pui-package-budget` uses this constraint to require `pui-validate` after numeric mutation, so retained pre-mutation cost evidence cannot satisfy a direct review handoff. This routing check does not certify evidence contents or authenticate a caller-supplied source identity.

Agent Operations coordinates multiple workflow families without flattening their domain-specific protocols:

- `issue-steward`: classify and route GitHub Issues;
- `pr-steward`: summarize pull-request state and route the next review or decision;
- `reposteward-pr-portfolio`: manually trial RepoSteward's read-only PR portfolio snapshot as an external `pr-steward` evidence source;
- `autonomous-maintenance`: delegate bounded discovery and remediation to the separate workflow under `internal/autonomous-maintenance/**`.

`autonomous-tasks.yaml` is the machine-readable catalog of deployed, manual, and candidate recurring task families. `autonomous-tasks.md` explains which parts actually run today. Candidate entries are designs, not active automation.

## Active path: intake, review, and exact-head integration

Agent Operations now has an active end-to-end local path. The hourly repository workflow and Event shadow provide sanitized intake and reconciliation signals. The credentialed local runner re-collects canonical live state, performs evidence-bound review, submits authorized dispositions, and integrates clean exact heads. Each lane has one job; the read-only intake token is not the capability ceiling of the downstream system.

The scheduled shadow runs once per hour at minute 17 UTC and may also be dispatched manually. It collects bounded Issue and PR facts, validates a structured route, and preserves artifacts. Event-driven delivery is the primary direction; until its controller is deployed, the hourly sweep is the automatic trigger and later becomes reconciliation fallback. The manually dispatched RepoSteward trial remains an optional external evidence source whose incomplete results stay visible.

The live GitHub repository is the source for Issue and PR state. Downstream mutation primitives always re-read it and bind actions to an exact target, so intake artifacts never become a second tracker or a portable authorization credential.

## ModelTrace at Agent write boundaries

The owner-authorized **dot-only exception** (2026-10-06) replaces measurement with visible `Agent: dot` and `ModelTrace: not measured — owner-authorized dot exemption (2026-10-06)` disclosure. For supported publisher commands, dot uses `--agent dot --dot-exemption owner-authorized-2026-10-06` instead of `--record`/`--context`; never mix them or invent a measured record. This is a role declaration, not authentication or action permission. All authorization, live-account, exact-head/tree, DCO, independent-review, CI and privacy conditions remain. An already authorized real connector may perform equivalent live checks when the local CLI cannot represent this exception; it must not fabricate a receipt, a `gh` response or a passed validator. The measured flow below applies to non-exempt Agents.

`pui-agent-identify` is the U0 `public-read`, disposable-output-only transition from `request-context` to `modeltrace-record`. It measures the active model with three directly emitted literal arrays and pinned offline closed-set ModelTrace scoring. For non-exempt Agents, a current content-bound record is mandatory before every Agent-originated commit, Issue/PR creation, material update, comment, review, or collaboration write, including human-assisted runs. Read-only/local work remains usable without sampling; humans and deterministic non-LLM automation have no model-testing obligation. Historical ingestion and published history remain unchanged.

See [Contributor Agents](contributor-agents.md#measure-and-disclose-the-active-agent-model) for scope, one-hour normal/fifteen-minute anomaly freshness, retesting, independent-context sampling, exact handoff digests, privacy and bypass limits. Only the fingerprint supplies measured `modelId`; system/harness labels are declared separately. Honest candidate, ambiguous, failed, low-confidence, unsupported/unknown, mismatch and retest-disagreement outcomes remain visible. The public receipt is unsigned and non-authenticated: no permission, rights, independent review, acceptance or pending scheduled-scope activation follows from it. Keep samples, private context/session IDs and private conversation/operational/account circumstances out of tracked artifacts and publications.

Bounded retests accept a retained prior receipt only from the same repository/session/context/route and exact declared labels, measured no later than the current response starts. The prior may have expired, but later or foreign-scope evidence cannot be linked as this attempt. GitHub owner/repository identity comparisons ignore casing without rewriting contexts, challenges, public receipts or their digests.

Fresh challenges, scoring and write admission require an opaque session alias generated with cryptographic randomness by the operator/runtime: 32-byte hexadecimal or UUIDv4. The accepted shape is not proof of entropy or backend identity. Historical descriptive-session records remain readable and recomputable, but cannot authorize a fresh write. `challenge` and `score` require a new private `--out` outside the checkout before input reads; stdout contains only the public output summary, never the private artifact. Both closed-set/context limitation anomalies are mandatory in runtime and receipt-schema admission.

The output parent is resolved and checked again immediately before exclusive creation. Retargeting that parent into the checkout during input reading or scoring therefore rejects before writing private material. This bounded recheck is not an atomic filesystem sandbox against mutation in the final check/write interval.

Before scoring, the existing challenge, response and prior retest-record inputs must also resolve outside the checkout, including directory aliases. Public receipt validation derives declaration unavailability, pinned-bank absence, declaration conflict and measured-label mismatch from the declared labels and measured result; omitted or spurious declaration anomalies cannot be hidden by rebinding an unsigned digest or expiry. This preserves the existing scoring and TTL policy, not backend authentication.

Failed public receipts require at least one missing valid sample. A null count with a null digest records a failed probe; a null count with a retained digest records strict sample-validation failure. Their diagnostic codes must match those sampling facts, and a valid count always requires a retained digest. `count-deviation` is present if and only if a retained non-null count differs from its corresponding pinned probe count; missing or invalid samples alone do not imply it. All three valid samples cannot be relabelled as a failed measurement by rebinding the unsigned receipt digest.

Each non-null receipt count must satisfy its corresponding probe's unchanged producer tolerance. Runtime admission and the JSON schema apply those bounds by position; another probe's wider range cannot make an impossible sample count canonical.

The shared renderer orders object keys consistently in every public format while preserving array order and receipt values. A private JSON round trip that changes only key insertion order therefore preserves both the receipt digest and exact public disclosure bytes. Publication markers use the case-normalized GitHub repository identity, so casing aliases cannot re-key an otherwise identical prepared publication.

At the standalone Markdown visibility boundary, a raw HTML `ModelTrace` h2 cannot supply or compete with the canonical disclosure, including inside ordinary nested HTML containers; fenced/commented/quoted examples remain non-disclosures. Nested canonical Markdown headings do not become standalone disclosures. Marker-free exact-body Issue creation binds duplicate candidates to Issue kind and the requested title before counting matches; a different title or prior PR may legitimately reuse disclosed template bytes. Marker-bearing mismatches still reject rather than create a compensating duplicate.

Commit preparation reads the exact configured-origin repository's current `default_branch` and rejects that branch, rather than guessing `main` or `master`. Unknown or foreign metadata fails closed, and the final binding rechecks the same default alongside branch, HEAD and tree. A differently named contributor branch remains usable; these separate reads do not make GitHub metadata and the subsequent local commit atomic or grant GitHub privilege.

Use the supported publisher surfaces below. Every invocation additionally requires `--repository github.com:owner/repo --record <record.json> --context <context.json> --mode human-assisted --mode-source current-user --authorization explicit-current-user` for that independently established, exactly authorized mode; `active-human-loop` is the other human-assisted source. Pending scheduled writer scopes remain blocked. Generate and include the exact public disclosure before sealing the message/body.

For durable owner delegation, the trusted launcher instead supplies the existing signed `--owner-authorization`, `--owner-key` and `--owner-grant` arguments, independently selected `--mode`/`--mode-source`, and `--authorization <same-grant-id>`. Local commits require `implement`; supported ordinary GitHub publisher operations require `collaborate`. Existing Issue/PR comments and body updates bind the actual target kind and number. Commits and creation of new objects require an explicitly granted repository portfolio (`*`), not an inferred Issue/PR scope. Signed state is rechecked at the final write boundary; this does not activate generic scheduled scopes or the separate evidence-publication leaf.

```sh
pnpm agent:identify -- challenge --context <context.json> --out <challenge.json>
pnpm agent:identify -- challenge-digest --challenge <challenge.json>
# The active model saves a genuine literal response; code does not generate samples.
pnpm agent:identify -- score --challenge <challenge.json> --response <response.json> --out <record.json>
pnpm agent:identify -- disclosure --record <record.json> --context <context.json> --format markdown
pnpm agent:publish -- commit --message-file <message.txt> --branch <branch> --expected-head <sha> --expected-tree <authorized-tree-sha> <required-boundary-flags>
pnpm agent:publish -- issue create --title <title> --body-file <body.txt> <required-boundary-flags>
pnpm agent:publish -- pull-request create --title <title> --body-file <body.txt> --base <base> --head <branch> <required-boundary-flags>
pnpm agent:publish -- comment --number <issue-or-pr-number> --body-file <body.txt> <required-boundary-flags>
pnpm agent:publish -- update-body --number <issue-or-pr-number> --body-file <body.txt> --target-updated-at <UTC-time> --target-body-digest <raw-body-sha256> <required-boundary-flags>
```

`update-body` is for a credential-owned target with the exact freshly read original body/time binding, never rewriting a human's original text. For prepared evidence comments, include the canonical disclosure in the authorized payload/hash before the publish transition. Existing `agent:review` submission/merge and `agent:collaborate` writers require `--record` and `--context` and preserve their distinct exact-action, rights, independent-review and authorization gates. Hooks use `PUI_AGENT=1`, `PUI_MODELTRACE_RECORD` and `PUI_MODELTRACE_CONTEXT`; disabled hooks, `--no-verify`, direct `git`/`gh`/API and token use can bypass local checks but never waive the mandatory policy. These helpers do not sandbox credentials or attest backend identity.

`agent:collaborate -- validate` is local, measurement-free request/handoff, purpose and eligibility verification. It retains explicit mode/source and structural artifact/digest requirements, but neither reads private ModelTrace files nor returns a measured receipt. It does not certify a write as ready: `apply` separately requires fresh scope-exact recomputation and exact record-reference/digest binding before any live read or mutation.

The commit publisher takes a prepared message without a `ModelTrace:` trailer and appends the current canonical trailer before `git commit --signoff --cleanup=verbatim`; a local commit needs no GitHub email or network privilege. Its independently authorized tree must match the staged index both initially and immediately before the commit. Do not blindly approve an index containing unrelated user work. A private index freezes that authorized tree for the actual commit, so later shared-index staging cannot enter it or be consumed. The immutable observed commit must retain the complete prepared message plus current disclosure and expected committer sign-off, authorized tree and exact first parent before success is reported; a post-write mismatch is unknown, not permission to retry. Private record/context filesystem paths must resolve outside the real checkout at initial and final admission, including directory aliases that can be retargeted.

Readback uses the stored commit object and its actual committer header, not `git log` presentation output. Configured display encoding or signature verification output cannot alter the message or signer used in the equality check.

Prepared Markdown uses the shared visible-disclosure parser, not a source-line regex. Closed fenced examples, comments and quoted examples receive the usual canonical append; an exact visible current receipt is byte-preserved. Wrong, malformed, duplicate or still-hidden disclosures reject before publication. Private-input final-component symlinks remain rejected by the existing no-follow reader; directory aliases do not waive checkout containment.

PR creation markers bind both exact pushed head and base revisions, the actual source repository, branch names and prepared payload. The checkout origin supplies that source repository, which is verified live rather than reconstructed from the base repository's name. A fork head uses `owner:branch`; same-organization forks also transmit the actual `head_repo` name. Readback and duplicate lookup bind that same source repository and revisions. Already disclosed, authorized Markdown bodies are transmitted byte-for-byte without another marker; their duplicate lookup cannot borrow an older closed PR's identical body. Public contributors may create Issues, comments and fork PRs with repository read access; publication does not grant push rights or require rewriting other contributors' history. A lost mutation acknowledgement stays unattributable even when an exact publication is observed; reconcile read-only and do not automatically retry.

The immutable base-to-head contributor comparison collects all documented API pages before publication, including sources beyond the unpaged 250-commit limit. Page totals must agree, commit identities must be complete and unique, and the final commit must match the exact pushed source head. Missing, repeated or inconsistent page evidence rejects before any PR creation; it is not permission to publish a partial comparison.

The squash merge request binds `commit_title` to `Integrate pull request #<number>`, rather than allowing the repository's PR-title default to introduce another current trailer. Its message quotes the sealed PR body and every historical commit message under its SHA before adding the current ModelTrace trailer. Historical `ModelTrace:` and `Signed-off-by:` text remains readable, not current identity or DCO trailers. The combined title and message must have one exact current disclosure before PUT. The final REST body must still match the sealed input, and measurement freshness is checked again after the last base-ref read, before PUT. After an acknowledged PUT, the fetched Git commit must retain that exact canonical trailer as well as the reviewed parent before a successful merge receipt is returned. Missing or changed disclosure reports the acknowledged commit as unverified and never repeats the PUT.

## Event shadow contract, not a deployed listener

`event-shadow.yaml` defines the first contract-only slice of the intended event-driven path. It does not register a webhook, deploy a listener or controller, receive a GitHub token, run a Coding Harness, or change the current scheduled workflow. The scheduled shadow remains the only automatic repository workflow described here.

The Event shadow runtime authenticates the exact raw request bytes with `X-Hub-Signature-256`, then cross-checks declared transport headers and payload identities against runtime-supplied repository, hook, installation, and dedicated-Agent anchors. GitHub's raw-body HMAC does not authenticate those headers, so they remain transport claims and never grant authority. Its normalized envelope contains identity and revision facts, not Issue bodies, pull-request bodies, comments, patches, commit messages, or filenames. An external contributor or fork may wake read-only collection; neither identity grants action authority.

The current allowlist covers selected `pull_request` lifecycle actions for offline shadow replay. The replay key binds the trusted repository ID to the authenticated raw-body digest instead of unauthenticated delivery or hook headers. Rewriting those headers therefore cannot re-key the same signed body; byte-identical deliveries collapse to one observation, which is safe because E0 can only request a fresh live read. A per-pull-request cursor detects older or tied revisions, but it does not pretend GitHub deliveries have a total order. Those cases return `reconcile-live-state`. An admitted event returns only `collect-live-state`; it is permission to observe again, not permission to review or mutate.

The CLI accepts a captured raw delivery, deployment-bound public trust anchors, and optional prior state. The webhook secret must come from a named environment variable. Schema-valid unique delivery keys may arrive in any order; the runtime canonicalizes them before producing its pure `nextState`. It does not persist or consume that state, so a future controller must provide the globally consistent store and atomic lease before deployment.

```sh
corepack pnpm@10.32.1 agent:event-shadow -- replay \
  --delivery <raw-delivery.json> \
  --trust <deployment-trust.json> \
  --state <prior-state.json>
```

Every envelope and receipt fixes `mutationAuthorized` to `false` and `writeOperationsPerformed` to `0` because this layer authenticates and orders signals; it does not carry a GitHub credential. An admitted event triggers canonical live recollection, after which `pui-review` and `pui-integrate` may act only under separate explicit current-user authorization or a future activated standing scope. A consumer that does not trust the process boundary must retain the signed raw body and reproduce normalization. A production controller still supplies durable replay storage, leases, acknowledgements, and independently authenticated transport provenance.

## Maintainer-controlled local review and integration schedule

The Codex desktop task `proto-ui` retains read-only observation and reconciliation for the three scheduled writer scopes. `proto-ui-scheduled-collaboration-v1`, `proto-ui-scheduled-review-v1`, and `proto-ui-scheduled-merge-v1` are all `pending-runtime-identity`; they do not authorize GitHub writes until a Poppy-specific signed/OIDC execution envelope is bound at the final write boundary.

The local repository cannot authenticate a Codex task name, and a process holding the live GitHub credential could bypass these scripts. The generic scheduled boundary is therefore read-only until broker-verified workload identity, repository/task binding, replay prevention, live permission, canonical input reconciliation, exact-head checks, and GitHub rules are enforced at the final write boundary. Independently verified durable owner delegation follows the separate ordinary-work path in [handoff.md](handoff.md); it does not activate these generic scheduled scopes.

Autonomous collaboration without verified owner delegation additionally remains blocked because trusted publication verification for a `governed-outcome` artifact is not implemented. A matching caller-supplied reference and digest cannot establish that authority, and changing a scheduled scope to `active` alone cannot enable this path. The future generic producer/publication contract needs a separate governed decision; explicit current-user collaboration retains its existing admission rules. Owner-delegated writes still require the same current ModelTrace record, exact target, live permission and final-action revalidation.

The intake token remains read-only. Downstream review and merge commands bind `commit_id` or `sha` to the inspected head, reconcile stale or unknown outcomes, reject review dispositions from the PR author or any commit author/committer platform identity, fail closed when a contributor identity is unavailable, never count an approval with unknown reviewer identity, preserve active `CHANGES_REQUESTED` even when its reviewer identity is unknown, require separately trusted CI and DCO conclusions plus resolved threads, and never force or bypass repository rules. Source/license provenance remains part of the independent content review; DCO success does not replace it. Those technical invariants enable automatic progress; they are not repeated human approval points.

Evidence publication credit requires the full rendered original packet body and both complete matching packet and Agent-evidence digest tokens in the same valid exact-head independent `APPROVED` review from a publisher whose current repository permission is verified as write or admin. Publication and duplicate checks preserve the full rendered disclosure, normalizing only CRLF, outer whitespace, and comments made entirely of exact receipt tokens. Mixed or unrelated comment content is retained; token-only or edited prose cannot supply publication credit or suppress a corrected review. GitHub maps the maintain role to its write base permission; read, triage and no-access approvals cannot supply approval or publication credit. Merge callers must retain and supply the original `--published-review-packet` artifact, bounded to 64 MiB; its file or self-computed hash alone supplies no authority. The current canonical input must differ from its original reviewed input only by that one publication review and the publisher permission newly introduced by it. The inverse removes exactly that review and removes only its author's permission when it is no longer an eligible approval subject, then validates the original packet and digest. A refreshed merge packet may change only `reviewInputDigest` and `observedAt`, preserving base/head, scope, findings, evidence and reconciliation. Other input drift needs a new review. The current canonical input cannot establish an additive comment's publication authorization, so a comment marker alone fails closed. A lost or malformed successful review POST response remains unknown after one read-only reconciliation even when a concurrent review matches the credential, head, disposition and body; only a fully validated successful POST object binds the invocation. An unknown receipt does not authorize retrying the POST; re-inspect the live review state before deciding any later action.

Both `agent:review -- submit-review` (including `COMMENT`) and `agent:review -- merge-pull-request` require independent `--mode` and `--mode-source` arguments. Existing write callers must add the context established by their launcher/operator before reading task-authored content, never copy it from a handoff. `human-assisted` accepts `current-user` or `active-human-loop`; `autonomous` accepts `maintainer-invocation`, `schedule`, or `governed-queue`. Missing or invalid declarations reject before artifact reads; conflicting handoff fields reject before reading input, packet, assessment, publication, prior packet or external-evidence artifacts and before any external call. Both fields must match exactly, and eligibility plus final review/merge authorization use the retained startup context. `input-digest` keeps its existing arguments. `validate`, `inspect`, `eligibility`, and `submit-review` additionally require `--prior-handoff <received-validation-input.json>` when their handoff originates at `pui-validate`; retain the actual input received by that validation step. Other review-intake routes and read-only v3/v1 ingestion remain supported. The predecessor is separate from `--prior-packet`, which binds a previous review packet; neither replaces the other.

These standalone CLI arguments are operator declarations, not runtime attestation or authenticated current-user instructions. A credentialed caller can forge matching arguments and files; the CLI is not a token sandbox. The trusted launcher must keep invocation context and credential access independent of task content. This declared-context binding does not activate any pending scheduled writer scope or relax publication, permission, CI/DCO, assessment, or exact-head gates.

The `pui-review` → `pui-integrate` handoff requires `review-packet`, `review-input`, `published-review-packet`, `mutation-authorization`, and the current content-bound `modeltrace-record`. Retain the original packet before publication; carry its exact file reference and canonical `sha256:<computeReviewPacketDigest(original)>` separately from the refreshed packet. Merge validates both that reference against `--published-review-packet` and that digest against the bounded, validated file content before collecting live input. Older integration handoffs must add the retained original and current Agent measurement before a new Agent write; they cannot enter integration by supplying CLI files alone. Terminal local-review handoffs remain valid without a published packet or ModelTrace measurement, and the packet/input schema versions and historical read-only paths are unchanged.

Review packets remain schema v2 unchanged. Before sealing a packet for a current submission, append the exact generated ModelTrace disclosure to `agentEvidence.source` with a preceding newline, so `## ModelTrace` renders as a standalone heading. Do not use observations for the disclosure: their list formatting can prefix the heading. Submission/merge require `--record` and `--context` with the exact same private record reference and canonical public-receipt digest on the handoff artifact; do not synthesize a new packet field or append an unsealed disclosure after hashing.

Canonical review-input v5 adds `reviewerPermissions`: stable GitHub collaborator-permission endpoint/source, observed login, base permission, repository and head bindings enter the digest. Every live collection fetches these facts from GitHub again; missing, mismatched or unavailable observations fail closed. Wall-clock `permissionsObservedAt` stays in the collection/submission receipt so unchanged facts can still compare equal. These facts establish current publisher eligibility, not historical user or Agent authorization. Version 4 inputs must be re-collected as v5; historical files are not rewritten or treated as certified. Canonical v3 input retains its original hashing and read-only validation, inspection and rendering path only for schema v1 `COMMENT` packets. It cannot enter `submit-review` or `merge-pull-request`; `APPROVE`, `REQUEST_CHANGES`, and merge require freshly collected v5 input and schema v2 Agent evidence. The final reads and write remain separate operations, so the helper does not promise atomic permission stability.

Canonical review collection follows every required connection: commits, reviews, conversation comments, review threads, each thread's replies, and the exact head commit's check contexts. GraphQL pages carry stable IDs, `totalCount`, `hasNextPage`, and `endCursor`; missing IDs, duplicates, repeated cursors, malformed pages, changing totals, request failures, or incomplete counts reject the whole collection. Changed files use explicit numbered REST pages with unique paths and the PR's reported count, bounded to 3,000 files. Every GraphQL connection is bounded to 100 pages and 10,000 items at 100 items per request; the complete invocation is bounded to 1,000 requests, 64 MiB per response and 256 MiB cumulative response bytes. Hitting a bound never returns partial canonical input.

Each page binds the same live repository/PR, base/head, viewer, permission and PR state. After collecting files and current reviewer permissions, the collector re-reads that state. It then repeats the complete collection and compares the canonical v5 digests and live execution state, detecting same-count edits, nested reply changes, check provenance and permission drift. Any observed drift rejects without a write or automatic retry; re-collect once the target is stable. Full commit messages, contributor/platform bindings and check provenance remain digest inputs. These consecutive observations do not make GitHub reads atomic or remove the final read-to-write race; review/merge still apply their independent exact-head authorization, CI/DCO, publication, permission and repository-rule gates. `agent:review:smoke` reports the verified count and canonical digest without submitting a review or merge.

Before a new `APPROVE` or `REQUEST_CHANGES`, the actual reviewer's canonical live disposition history determines whether a prior governed packet must be reconciled. A complete published packet token binds its digest and reviewed head; a caller cannot opt out with null pointers, a later comment, or an older selected artifact. The exact `--prior-packet` and complete finding reconciliation are then required. An unavailable artifact blocks the disposition instead of being synthesized. Rendered schema v2 reviews state the exact base as well as the head. Disposition duplicate detection accepts the identical packet receipt or a genuine original `--prior-packet` whose publication-only input change is verified; matching visible prose alone cannot suppress a review of changed input. Existing dismissal semantics, `COMMENT` disclosure and this bound duplicate no-op remain available; this does not certify historical publication authority.

The merge writer requires the target-bound reviewed packet, the original published approval packet, canonical input and execution context. It rejects a missing or changed original before any external read, and verifies its live publication binding again after collection. It owns a fresh v5 collection and runs the same complete eligibility gate again, including trusted CI/DCO, independent approval/publication evidence, current reviewer permissions, and unchanged acting credential. A caller-provided `allowed` flag or callback cannot replace that collection. The final REST PR read must also report `mergeable: true` and `mergeable_state: clean`, or `mergeable_state: unstable` only when the writer's fresh collection satisfies the same verified Vercel preview-authorization exception. A caller-provided allowance cannot waive this final gate. The helper re-reads the PR head/base and actual base ref before its single PUT, then binds a successful receipt to the resulting commit's single parent and the inspected base. GitHub has no base-SHA compare-and-swap parameter for that PUT: a base change after the final read can still merge irreversibly, and a different result parent yields an unbound outcome rather than a receipt for the old base. After a confirmed successful PUT with a commit SHA, verification uses at most 12 read-only attempts with one-second programmed delays for stale visibility or recognized transient failures. A real HTTP 429 response, or HTTP 403 with a real `Retry-After` header or `X-RateLimit-Remaining: 0`, follows [GitHub's rate-limit guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#handle-rate-limit-errors-appropriately): `Retry-After`, then exhausted-primary-limit reset time, or otherwise a one-minute exponential backoff, within a fixed 120-second cumulative rate-limit wait budget. An excessive or malformed delay stops verification rather than shortening the server's wait. Response headers, not body/stderr wording, select this path; ordinary permission-denied 403 responses stop without retry, as do invalid or incomplete timing headers. GitHub documents both status codes in its [primary and secondary rate-limit responses](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit). Unknown PUT outcomes never enter this path. Authorization denials, conflicting identities and malformed evidence stop verification. A lost/unknown PUT still receives only one read-only reconciliation and never gains this successful-response polling or an attributable receipt. No path repeats the PUT or automatically rolls back a merge.

GitHub readiness requires `MERGEABLE`/`CLEAN` or the [narrow verified Vercel preview-authorization exception](contributor-agents.md#review-as-an-evidence-packet). The exception permits `MERGEABLE`/`UNSTABLE` only for the verified `vercel` Bot's terminal `https://vercel.com/git/authorize` failure when every other check is terminal with `SUCCESS`, `SKIPPED` or `NEUTRAL`. Real deployment failures, `BLOCKED`, conflicts, other failed or pending checks, and all independent review, trusted CI/DCO, evidence and repository-rule gates remain blockers. The preview-authorization exception requires structured `previewAuthorization` publication debt bound to the collected status URL, `WRITE`/`MAINTAIN` permission, and an explicit live `viewerCanMergeAsAdmin: false`. Admin, bypass-capable, or unknown capability cannot use it; mentioning Vercel in unrelated debt is insufficient. See the [canonical Agent policy](contributor-agents.md#review-as-an-evidence-packet).

## Execution boundary

The hourly scheduled and manually dispatched workflow in `.github/workflows/agent-operations-shadow.yml` uses this sequence:

1. check out the default-branch repository state with persisted Git credentials disabled;
2. collect a bounded GitHub snapshot using read-only repository permissions;
3. validate the versioned policy, workflow registry, schema, and fixtures;
4. run the commit-pinned Codex Action with Codex CLI `0.138.0`, the `:read-only` permission profile, and no network access when `OPENAI_API_KEY` is available;
5. validate the structured report against the snapshot and Phase A invariants;
6. upload the input and report as artifacts without writing from the intake credential; eligible exact-target continuation is handed to the credentialed local mutation leaves.

Issue and pull-request bodies are untrusted data. The collector strips HTML comments and control characters, applies length bounds, and records truncation. Deterministic validation, exact-action authorization, and live preflight keep authored text in the evidence plane while allowing eligible work to continue automatically.

## Decision boundaries and standing automation

The default is `none`: ready governed work continues through claim, implementation, validation, review, ready-for-review, and exact-head integration. Only two decision classes interrupt that path:

- `unresolved-product-direction`: existing authority cannot decide a material semantic, ownership, public-guarantee, lifecycle, or compatibility choice;
- `privileged-or-irreversible-operation`: publication, release, access, secrets, rulesets, security disclosure, a provenance exception, or another action that cannot be safely bounded and recovered.

A decision packet asks only for the unresolved choice and names the automatic continuation. Finding disposition, commit grouping, review disposition, and merge are evidence-driven workflow states rather than separate human gates.

## Collaboration execution contract

A collaboration request names exactly one of the seven actions in `proto-ui-scheduled-collaboration-v1`, carries an empty attended-decision list, binds current-user instruction or governed-outcome evidence, and includes the exact repository, object identity, `updatedAt`, and head, base, thread, or workflow identity that the action needs. Metadata requests carry complete expected and desired metadata; update-branch requests bind `expected_head_sha`; ready-for-review carries validation evidence; thread resolution and CI rerun carry resolution or diagnosis evidence; bounded comments receive a request-digest marker.

Current `agent:collaborate -- apply` additionally requires `--record` and `--context`, with the exact same private record reference and canonical public-receipt digest on the handoff's `modeltrace-record` artifact. Local `validate` does not require these inputs or bind a current measurement. Current receipts use schema v2 with public `modelTrace`; its scope must match the receipt repository, permitting equivalent validated GitHub casing, even when no original request is supplied for ingestion. A supplied request additionally binds that same repository and exact action/target. Historical v1 ingestion remains read-only compatible; receipt ingestion does not renew or require current measurement freshness. GitHub's update-branch API cannot bind its generated commit message to the exact ModelTrace disclosure. A behind branch therefore rejects the current mutation and directs an authorized local merge with `--no-commit`, followed by a controlled `agent:publish -- commit`; re-collect the new head for later collaboration. An exact already-satisfied base remains a zero-write no-op. This does not authorize another branch or bypass its permissions/rules.

Include the canonical public disclosure in authorized comments and actual body replacements before request sealing. A title/label-only repair preserves the historical body; it does not trigger a silent body rewrite or retroactive disclosure insertion.

Both `validate` and `apply` require independent `--mode` and `--mode-source` arguments, including when the handoff already contains those fields. Migrate existing invocations by supplying the mode established by the trusted launcher or operator before reading task-authored content; never copy the arguments from the handoff. `human-assisted` accepts `current-user` or `active-human-loop`; `autonomous` accepts `maintainer-invocation`, `schedule`, or `governed-queue`. Missing, invalid, or conflicting declarations reject before external reads, and both fields must exactly match the handoff. Admission and the final writer retain the independent invocation context. Human-assisted purpose evidence must include `current-user-instruction`; `governed-outcome` alone does not qualify. `request-digest` and read-only `thread-revision` keep their existing arguments.

These standalone CLI arguments and evidence references are operator declarations, not runtime attestation or authentication of a current user instruction. The repository cannot authenticate matching forged arguments and files, and the CLI is not a token sandbox. A trusted launcher must keep invocation context and credential access independent of task-authored content. The checks establish declared-context consistency and live admission; autonomous collaboration still fails closed pending trusted publication verification.

For thread resolution, first run the read-only `agent:collaborate -- thread-revision --repository <github.com:owner/repo> --pull-request <number> --thread <thread-id>`. It needs no sealed request and emits the exact `target`, including `threadUpdatedAt` and `threadRevisionDigest`, plus the observed resolution/outdated state. Copy that target into a new request, supply the authorized expected/desired state and resolution evidence, then seal it with `request-digest`. A missing digest requires fresh collection and a newly authored request; no command inserts a default digest or silently upgrades historical inputs. Keep the original bytes as historical evidence.

The thread digest binds the thread ID and every collected comment's database ID, author login (or an explicit null for a deleted account), exact body, and update timestamp, sorted by ID. It detects same-timestamp additions, edits, and deletions and participates in preflight, the final admission read, already-resolved no-op detection, and post-write verification alongside the existing head, permission, and time boundaries. Empty threads, malformed comments, missing/duplicate IDs, and incomplete pagination fail closed. Collection retains the existing one-page limit of 100 comments and rejects truncation. The digest is change detection, not identity, authorization, resolution evidence, or an atomic snapshot; GitHub's read-to-write interval still has no server-side compare-and-swap guarantee.

Run `agent:collaborate -- request-digest` after the request is complete, then put `sha256:<requestDigest>` on the handoff's `collaboration-request` artifact and the exact authorization ID on its `mutation-authorization` artifact. Autonomous handoffs also bind the loaded self-assessment through the `capability-envelope` digest. `apply` rejects a stale or mismatched preflight before writing, emits a zero-write receipt when the desired state is already live, or performs one supported write followed by verification. A missing pull-request author does not confer ownership; independent-review requests reject unavailable author identity. An already-updated branch is a pre-write no-op only while its head still equals the requested head and its exact base is satisfied; current behind-branch writes reject as described above. Ready/thread GraphQL writes require an error-free acknowledgment of the exact requested object and desired state; invalid acknowledgments remain ambiguous after one read-only reconciliation, even if a concurrent actor reaches the desired state. Supported mutations use one verification read. A bounded comment's exact request marker, canonical body, acting credential, and creation time establish idempotent live state. A comment request dated after the initial or final live preflight observation is rejected before writing; equality is allowed. These observations use the collector clock and do not provide server-clock synchronization. A successful comment POST instead binds its returned object ID, acting credential, exact canonical body, and valid server creation timestamp to the unique live readback at the requested target and head; it does not compare that server timestamp to unsynchronized local clocks. A pre-existing marker still requires the conservative creation-time window for a zero-write no-op. The deterministic request marker cannot identify which invocation wrote it, even with the same credential and timestamp: every unknown outcome stops after one read-only reconciliation and says not to retry blindly. For bounded comment POSTs, an unavailable response, failed or invalid readback, or invalid receipt raises `CollaborationMutationUnknown` with a separate `proto-ui.collaboration-unknown` result; the CLI emits that JSON and exits nonzero. This result records one `writeAttempts` and one `reconciliationReadAttempts`, including a failed read. Its `acknowledgementReceived` flag means a non-null parsed POST response was received, not that it passed provenance validation. It contains static failure guidance and request/target bindings, without a verified post-state or success receipt. Library callers catch the typed error and inspect its result kind; CLI callers must check both the nonzero exit and result kind. This failure result is not a collaboration-receipt handoff and supplies no approval or retry authority.
