# Thin compiler: atomic lowering and completion

## Authority and purpose

This is the compiler engineering and acceptance standard selected by the maintainer on 2026-10-29. It is not a new public semantic entity, a promotion of draft contracts, or evidence that current outputs already comply. Applicable `spec/**` entities and lifecycle retain their authority; unresolved semantic contradictions must be defined and reviewed there, not hidden in emitters. The [dated decision record](../records/2026-10-29-thin-compiler-direction.md) preserves the observed baseline and outstanding work.

The compiler translates authored prototype logic and reached atomic abilities into the most direct correct target representation. Compile-time parsing, checking, normalization, IR and lowering are necessary tools. Their structures must not be shipped merely to interpret or translate them again at runtime. A tiny special path, a minimal Button demonstration, or a transitional common interpreter is not completion.

## Architectural red lines

1. **Independent shared definitions.** Prototype and compiler independently implement shared definitions. Do not copy a Button, Transition or other component protocol into a helper; do not dispatch by component name, export name, source path or package identity to choose business behavior. Package recognition alone is not proof of a violation: an atomic intrinsic must instead be justified against its generic capability definition. A source-level rename/re-export must not change semantics or demand selection.
2. **Compile abilities, not component identities.** Expand valid authored composition into a compile-time semantic representation; lower its state, trigger, hover, focus, accessibility and other actual abilities. Do not alter valid prototypes, ban their legal closures or omit behavior to fit an emitter.
3. **Final target representation.** Statically known templates, fields, operations and capability calls become native constructs. No emitted Proto IR evaluator, universal operation interpreter, runtime template-to-host translator, or copied semantic protocol may remain as the final implementation. Preserve genuinely dynamic data and independently specified language semantics; do not substitute target-language defaults for NaN, signed zero, UTF-16 ordering or single-evaluation guarantees.
4. **No second framework.** React uses React reactivity/lifecycle and normal component exports; Vue3/Vue2 use their own reactive/template and component conventions; Web Components use native custom-element lifecycle; GPUI uses its native state/ownership/render/event facilities. Consumers use ordinary imports, props, events and children/slots. No special Proto launcher or parallel framework runtime is required for source output. Keep the explicitly runtime-backed legacy profile honestly labeled, not counted as source-profile completion.
5. **Only reached support.** Compute the transitive capability/helper closure at compile time. Generate or import only necessary support. Overlay/geometry/platform mediation can be legitimate host APIs; event callbacks, target-native reactive state, identity, resource ownership and cleanup are not forbidden because they execute at runtime. Every such unit needs a specific reached requirement, not an all-features factory by default.
6. **No cosmetic certification.** File names, an implemented registry entry, source presence, one passing test, copied SDK size and compiler acceptance are distinct facts. Generated bytes, production-retained bundle/link bytes and initialization/registration/allocation work are three separate measurements. Report none as a proxy for another, and do not invent percentages.

## Ordered full delivery checklist

All rows below require exact source/head, owner, applicable definitions, implementation, positive/negative tests, real consumer evidence and remaining debt. Unchecked work stays unfinished; bounded patches only control review and regression risk.

1. **Inventory and semantic boundary:** enumerate every admitted parser/IR operation and declaration; trace authored source -> IR -> emitter -> generated imports/calls. Include expressions/control flow, state/props/events, lifecycle, template/children/slots, context, style, accessibility, focus/trigger and all module/host operations. Identify component protocol copies and type/name heuristics separately from legitimate atomic host mapping. Coordinate existing owners; do not take over frozen private work.
2. **Compile-time demand and typed representation:** determine reachable bodies and helper dependencies, and the runtime facts that cannot be reduced at compile time. Test closure transitively, including omission of unused abilities and retention of required cleanup/context. A new unused plan object does not satisfy this step.
3. **DOM source lowering:** complete React, Vue3, Vue2 and Web Components end-to-end native lowering and support selection. Replace aggregate support inclusion/eager initialization with reached units; integrate each target's native reactive and lifecycle mechanisms. Track concrete work in [#1055](https://github.com/Proto-UI/Proto-UI/issues/1055).
4. **GPUI direct representation:** lower templates and typed operations directly to Rust/GPUI; replace semantic `Value::Template`/generic projection interpretation where the IR already determines representation. Preserve numeric/string/evaluation semantics, native ownership, events, focus, accessibility and mixed children. Track [#1056](https://github.com/Proto-UI/Proto-UI/issues/1056).
5. **Protocol and heuristic removal:** use existing [#1018](https://github.com/Proto-UI/Proto-UI/issues/1018) history for Transition protocol drift; revalidate its current status/owner and remaining criteria rather than duplicate or imply it is reopened. Move authored protocol behavior to ordinary source lowering with timer/ViewIntent host atoms. Review overlay role defaults and `focusSelf` name-based parameter inference with independent red tests before choosing the appropriate definition/implementation owner. Do not blindly delete every intrinsic.
6. **Whole consumer conformance:** cover every accepted operation family on every implemented source backend, independently then in composition. Use empty prototypes, real authored Button and nontrivial composed trees as baseline journeys, not a substitute for the full matrix. Native/framework components and compiled components must interoperate through normal props/events/slots/imports, with repeated reactive updates, mount/unmount, detach/rebind, reentrancy, interrupted input and cleanup.
7. **Cost and artifact proof:** retain generated output/import graphs, clean consumer builds, optimized production-retained artifacts and initialization traces bound to exact inputs. Reuse [#758](https://github.com/Proto-UI/Proto-UI/issues/758) measurement governance. Count only applicable validated rows; preserve negative controls, failures and unsupported diagnostics.
8. **Completion and migration:** independent review, applicable exact-head checks and accepted consumer journeys must cover the full selected matrix. Record old/new artifact compatibility and any explicit lifecycle decision. No unresolved row silently becomes N/A; no gate is weakened to manufacture completion. Existing [#732](https://github.com/Proto-UI/Proto-UI/issues/732) and [#733](https://github.com/Proto-UI/Proto-UI/issues/733) remain pipeline/native-mixing coordination, and [#1024](https://github.com/Proto-UI/Proto-UI/pull/1024) remains separate relational semantics work.

## Backend and evidence matrix

| Backend | Source profile at audited baseline | Required final consumer proof |
| --- | --- | --- |
| React | Implemented; full thin conformance not established | Ordinary component import, React reactive updates/lifecycle, props/events/children, native mixing |
| Vue3 | Implemented; full thin conformance not established | Ordinary component import/template, native reactivity/lifecycle, props/emits/slots, native mixing |
| Vue2 | Implemented; full thin conformance not established | Supported Vue2 component conventions/reactivity/lifecycle, props/events/slots, native mixing |
| Web Components | Implemented; full thin conformance not established | Ordinary custom-element use, properties/events/slots, connect/disconnect/rebind cleanup |
| GPUI | Implemented; full thin conformance not established | Ordinary Rust import/use and native GPUI consumer, typed/template lowering, ownership and cleanup |
| Qt / Flutter / SSR | Not implemented in the audited public target registry | Explicit unsupported state; separate implementation and acceptance required, not inferred from files |

For each implemented row, cross all admitted operation families with positive controls, semantic negative controls and actual generated consumers. Include source/component/export rename controls, required-helper removal mutations, reordered/double-evaluated side effects, identity and lifecycle interruptions. Preserve original evidence bindings: old fixed-source executions do not certify a new combined source tree. Framework/library dependencies must be disclosed; ordinary target APIs are not a hidden Proto interpreter.

## Delivery discipline

Use bounded claimed work and normal repository handoffs. Preserve original authorship, DCO, failed checks and review independence. Static candidate preparation is not executed acceptance. New fixed-source execution, deployment and protection changes retain their existing permission boundaries. Updating this engineering standard does not waive any of them or authorize takeover of [#902](https://github.com/Proto-UI/Proto-UI/issues/902)'s frozen source bank.
